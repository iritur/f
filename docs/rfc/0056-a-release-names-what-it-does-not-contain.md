# RFC 0056: A release names what it does not contain, and a package identifies itself

- Status: accepted
- Date: 2026-09-04
- Affects: `RELEASING.md` (three new sections: *Release 0.2, and the four
  numbers that are not in it*, *From the package alone*, *Finishing one, which
  an agent does not do*), `xtask` (`sweep_commit` gains a second source,
  `manifest_commit` and `manifest_names_this_tree` beside it, `packaged_sweep_route`
  and the `sweep` line it writes into `MANIFEST`, `claims_block` and the
  `MANIFEST` header it writes, and a `--dry-run` that prints that header),
  `DATAPATH_GAP` and the check `lint-claims` now makes of it.
  Pays `E1-R02`. Extends RFC 0021 — which decided how a release
  handles a content that does not exist — to the case it did not cover: a
  *number* that cannot be produced at all. Reverses nothing.

## Decision

**Three things, and the first is the one that matters.**

**A release states its absences in the same document that states its contents,
with the chain that produces them named.** Release 0.2 is G1's release and G1 is
the datapath, and the four datapath claims `E1-P10` registers — ring submit
under load, doorbells per operation, copies per operation, kernel entries per
operation — are not in it. `E1-P10` needs `E1-B09`; `E1-B09` needs `E0-B15`,
which built the user-interrupt path as far as *refusing to construct* because no
machine this project can reach reports the hardware; and independently of all
three, every one of the four is a time, `bench/src/lib.rs` refuses to record a
timing in a container, and `E0-D10` owns the class-A machine that has not been
obtained. So the four cannot be produced on any machine this project currently
has. `RELEASING.md` says so, names the four tasks, and says what would have to
become true instead — all three of hardware, a machine and four registered
entries, and the first two in either order.

**And it is data, not only prose.** `DATAPATH_GAP` in `xtask` declares the two
reasons as needles — the `!hardware.user_interrupts` refusal in `Bell::new`, and
`WHY_CONTAINER` in `bench/src/lib.rs` — and `lint-claims` requires both to still
be present. This is `OWED_REVERSALS`' and `CHAOS_GAP`'s mechanism (RFC 0036)
pointed at an absent *number* rather than at a present deviation, and the reason
for reaching for it is the one RFC 0036 gives: the failure mode of a gap in
prose is not that it is never closed, it is that it *is* closed and the
documents go on describing it. The day either needle goes, the build names the
section in `RELEASING.md` that has to be deleted. Two rows and not one, because
either reason alone is sufficient and the row that goes first says which half of
the section stopped being true.

**A release package identifies itself without a repository, and says whether it
can.** `sweep_commit` reads git first and, when git cannot answer, reads the
`commit` line out of a `MANIFEST` at the tree root — which is what an unpacked
package has and a checkout does not. `manifest_commit` fails closed three times:
the line must begin `commit` at column zero, its value must be forty lowercase
hex digits, and at least one file the manifest names must be present with the
hash it states, so that a manifest left over from another release is refused
rather than believed.

The second half of that is the one review found: the fallback lives in
`xtask/src/main.rs`, a stranger reaches that file only through `source.tar`, and
`source.tar` is `git archive` **of the commit** — so a package built while the
fallback is uncommitted carries a source that cannot do what the document says.
That is not a hypothetical, it is what the first draft of this RFC shipped. So
the packager reads the source it is about to ship and writes `sweep   from
MANIFEST` or `sweep   needs a repository` into the manifest, `--dry-run` prints
it, and `RELEASING.md` tells the reader to believe that line rather than the
section. A document cannot state this property, because the document is right
about the tree and the question is about the artefact.

**The package's manifest carries the claim statuses, derived.** `MANIFEST` opens
with a tally and one line per claim — six gating, one tracked, eight pending, at
the commit this was written — generated by `claims_block` from the same
`claim_files` and `claim_value` that write `claims/snapshot.json`.

## Context

`E1-R02`'s exit is *a third party runs a seed sweep and the four datapath claims
from the package alone*, and half of it is unmeetable by construction. That is
the finding rather than an obstacle to working around, and it produced the shape
of this RFC: the half that can be true was made true and measured, and the half
that cannot was written down where a reader of the release will find it.

**On the numbers.** The temptation with a claim that cannot be measured is to
publish something adjacent and let the reader do the substitution. `E0-B15`
already refused that once — the boot reports a doorbell count over the two
operations a self-test performs, and its exit says in as many words that this is
not *doorbells per operation under load* and is deliberately not registered.
Publishing it as one at release time would have undone that refusal at the last
moment, when nobody is re-reading exit lines. The contract at the top of
`RELEASING.md` decides it anyway — *a number that cannot be reproduced from the
package is removed from the package* — and RFC 0021 is the precedent for the
adjacent case: a *content* that does not exist is a predicate over the registry
and a named owner, never a quietly shortened list. This is the same discipline
applied one level down, to a number rather than to a content, and the mechanism
is the same: the absence is named and owned rather than left for a reader to
notice.

**On identifying the package.** `E1-R01` published one command for a sweep and
then measured it from an unpacked package, where it stopped with `cannot read
the commit from git: git rev-parse HEAD failed`. Three ways out were live. Teach
the sweep a `--commit <sha>` flag: rejected, because the value would then be the
stranger's assertion, typed by hand, and a mistyped commit produces a report
that is confidently about the wrong tree. Ship a repository inside the package:
rejected, because `git archive` producing files and no `.git` is precisely what
makes the source hashable, and a `.git` directory is neither reproducible nor
small. Have the packager write something the tree can identify itself from:
chosen, and it needed nothing written, because `MANIFEST` already carries
`commit <sha>` and is already hashed into the address the package is named by.

The cost of that choice is one instruction: the package tar and its `source.tar`
must be unpacked into **one** directory, so that `MANIFEST` lands at the root of
the tree. `RELEASING.md` says so with the commands. It is a smaller cost than it
looks, because the package's own copies of the eight contents sit at the same
relative paths as the source's and overlay byte for byte at a clean tag whose
line endings are what the repository says they are — which is itself a check a
stranger can run, and which this checkout fails. See *Found while measuring the
overlay* below.

**On the manifest carrying claim statuses.** `claims/snapshot.json` is already a
content of the package, so a second copy needs an argument. It is this: the
snapshot is *the registry, serialised*, and it is what a document renders a
number from. The manifest is the only file in the package that is about **the
package**, and `RELEASING.md`'s second stopping condition is a statement about
which claims gate. A reader who opens the archive should not have to know that
`claims/snapshot.json` exists in order to learn what the release asserts. Both
are generated from the same two functions, so a status change moves both or
neither, and neither can drift from the registry — which is also why the new
`RELEASING.md` section states no counts of its own. Prose is the copy that goes
stale, and it was the copy this task was asked not to write.

## Consequences

**Easy.** A stranger holding only a package whose `MANIFEST` says `sweep   from
MANIFEST` can run the published sweep. The absence of the datapath numbers is
now something a reader is told rather than something they have to infer from a
registry listing. Anyone opening `MANIFEST` sees what the release asserts and at
what strength, without a second file.

**Measured, and the qualifier above is why.** The first version of this RFC
asserted the sweep route in the present tense and review found the assertion
false against the very package this task built: unpack it as the document says
and the sweep still stops with `cannot read the commit from git`, because the
fallback was uncommitted and `source.tar` is `git archive` of the commit. What
was measured after that:

- The genuine package, unpacked with its `source.tar` into one directory, no
  `.git`, with the fallback spliced into the shipped `xtask/src/main.rs` and
  nothing else changed: `cargo xtask sweep 1 1` prints `commit
  7f3c3c0dab0b…` from `MANIFEST` and reports a clean trial. That is the route
  end to end, one file short of a commit.
- The same tree with the shipped `xtask` untouched: the old refusal, which is
  what the new `sweep   needs a repository` line predicts and prints in the dry
  run.
- Absent, malformed and foreign manifests all refuse, and a manifest whose
  commit line was replaced by forty zeroes with its hash rows left alone is
  accepted — the limit stated under *Foreclosed*.
- All six gating claims run in a tree with no repository and exit 0. That is not
  a formality: `sweep_commit` needed teaching, and nothing but the run said the
  claims did not have the same dependency.

**Hard, and deliberately.** `RELEASING.md` now contains a section about one
specific release, which is a document that will need editing when 0.3 goes out.
That is accepted rather than solved: a per-release notes file would be one more
document nobody re-reads, and the alternative — the honest-status page — is
`docs/TESTING-STATUS.md`, which is a content of the package and is where a
sentence about the doorbell hardware already lives. The reason it is not there
is worth recording: that page describes what has been built and tested, and this
is a statement about what a *release* does and does not assert. The two are
adjacent and are not the same, and `RELEASING.md` is the contract this is a
clause of.

**Foreclosed.** A sweep run in a tree that has a `MANIFEST` at its root and no
git now reports a commit rather than refusing. If a `MANIFEST` file for some
unrelated purpose ever appears at the root of a checkout, git still wins there,
so the exposure is limited to trees with no repository at all — but it is real.
Two things stand between it and a report naming a commit nobody has: the value
must be forty lowercase hex digits, and one file the manifest names must be here
with the hash it states. The second is what catches the ordinary version of this
— two releases unpacked into one directory, or a manifest left behind from an
earlier one — and one matching row is enough, deliberately, because requiring
the first row to match would refuse a package a stranger has edited to chase a
finding, which is the reason somebody unpacks one at all.

What neither check can do is detect a manifest that is internally consistent and
false, because the hash rows and the commit line are in the same file and
whoever edits one edits the other. Nothing inside an unpacked package can: the
package's address is over the archive and is not a member of it. Measured, so
the limit is stated rather than implied — a manifest whose commit line was
replaced with forty zeroes and whose rows were left alone is accepted, and the
sweep reports that commit. The answer to that is the address, checked outside
the package, and the reason a finding from an unpacked package carries no `git
switch` line is the same one.

**Not changed: the tree is still called dirty.** An unpacked package is exactly
its commit by construction, and nothing inside it can check that it still is
after a stranger has edited a file. `sweep_dirty` reads a git that cannot answer
as dirty and keeps doing so, so a finding from a package carries the commit
without a `git switch` line in front of it. That is the answer that claims least
and it is the same rule `E1-R01` wrote for a checkout with uncommitted work.

**Found while measuring the overlay, and not fixed here.** The package reads
the **working tree** and `source.tar` comes from the **tree object**, so the two
disagree wherever a checkout disobeys `.gitattributes`. This one does: 28
tracked files are CRLF on disk while `* text=auto eol=lf` and their committed
blobs are LF, and three of them are under `docs/rfc/` — a content of the package
— so they are in the package with CRLF and in `source.tar` without. `git status`
reports every one of them unmodified, because it compares after normalising and
the packager does not. The three are `0041`, `0048` and `0050`; `0054` is CRLF
on disk too and is untracked, so it is in the package and not in `source.tar` at
all, which is a different thing and not this one. The consequence is not
cosmetic:
**the address moves with the checkout's line endings at a fixed commit**, which
is the one thing an address exists not to do, and the two-runner comparison in
the pull-request gate cannot see it because both of its runners are Linux.

The check `RELEASING.md` first offered for this — `git add --renormalize .`
producing no diff — does not detect it, and that was measured rather than
assumed. Renormalising runs the working-tree bytes through the attributes and
compares against the blob; the blob is already LF, so a file committed correctly
and re-saved with CRLF afterwards renormalises to what is already there and
produces no diff. `docs/rfc/0041` is CRLF on disk, absent from the renormalise
diff and reported unmodified by `git status`. `git ls-files --eol` names all 28,
and it is what the document says now. The general shape is worth keeping: a
check built out of the same normalisation the defect hides behind agrees with
the defect.

It is written down rather than fixed because the fix is a choice this RFC should
not make on its own. Normalising the files is a working-tree edit with no
git diff behind it and no argument that it will not happen again; making
`content_files` read blobs out of the tree object instead of the working tree is
the real repair, and it changes what a package *is* — today `--dry-run` shows
you the tree you are standing in, which is why an uncommitted change shows up as
a different address rather than being silently packaged away. Whoever takes it
owes that argument and a `--dry-run` that still tells the truth.

**Not changed, and this one stops a release.** `RELEASING.md` gate 4 is that
`docs/TESTING-STATUS.md` has been re-read against the tree. At the time of
writing it has not been: it says the claims registry has three entries and none
gating, that L1 has no seed sweeps, and that L4 is instrumentation with no
hostile-peer fuzzer — and the tree has fifteen entries with six gating, a sweep
with a committed corpus, and two fuzzers. Preparing this release does not close
that gate, and this RFC records it rather than leaving the next person to
discover it on the day.

## What would reverse this

- **The section about 0.2 outliving 0.2.** If a *Release 0.3* section is added
  beside it rather than replacing it, `RELEASING.md` has become a changelog and
  the per-release material should move out of the contract into a file of its
  own, which is the thing this RFC argued against needing and would be wrong
  about.
- **A stranger unpacking the two tars apart.** The one-directory instruction is
  the mechanism's whole cost, and it is an instruction rather than a check. If
  somebody reports the sweep refusing from a package, the fix is for the
  packager to write the commit into a file `git archive` also carries — `git
  archive --add-virtual-file` is the tool — at the price of `source.tar` no
  longer being byte-identical to a plain `git archive` of the commit, which is a
  property a stranger can currently verify and would lose.
- **A release packaged from a checkout that disobeys `.gitattributes`.** If two
  machines at one commit produce two addresses and the paths matched, line
  endings are the next thing to look at, and the repair is the one above:
  `content_files` reads the tree object rather than the working tree.
- **A fourth status word in the registry.** `claims_block` prints `gating`,
  `tracked` and `pending` in that order and anything else after them, so a new
  word appears in the manifest rather than vanishing from it. If the tally and
  the rows ever disagree, that ordering is where to look.
- **`manifest_commit` being renamed.** `packaged_sweep_route` searches the
  shipped source for that name, so a rename makes a capable package say `needs a
  repository` — pessimistic, and a nuisance rather than a lie. If it happens, the
  repair is to unpack a package and sweep it in the release job, not to loosen
  the search into something that matches whatever the function is called next.
- **A package that says `from MANIFEST` and cannot.** That is the search being
  wrong rather than the mechanism, and it is the failure worth watching for,
  because it is the direction this whole line of repair exists to close. One
  unpack-and-sweep in CI settles it permanently and costs a job.
- **The four claims becoming producible.** The day `E0-D10` has a machine and
  `E1-B09` has hardware, `DATAPATH_GAP` goes red — that is what it is for — the
  section naming their absence is deleted rather than amended, and `E1-P10`
  registers four entries whose statuses appear in the manifest block by
  existing. That is the reversal this RFC most wants.
- **`DATAPATH_GAP` being emptied because the work *could* be done.** The same
  warning `OWED_REVERSALS` carries, for the same reason. A row goes when the
  needle it names goes, and what replaces it is a registered claim with a
  baseline and a reproduction.
