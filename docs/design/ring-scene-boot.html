Implementation companion to The Fast Path

Ring, Scene, Boot

Four parts at the level where the design decisions are actually load-bearing: the ring protocol that replaces the system call, the compositor that replaces the window system, the semantic layer that feeds it, and the phase-00 bring-up you could open an editor and start on. The architecture document argues these are the right choices. This one is about getting them right — and, for part III, about how it would fail.

Part I

The ring protocol

01

What it has to survive

Bet 02 says every service is a ring. That makes the ring the single most consequential piece of code in the system — and it has a harder job than io_uring does, because some of its peers are isolated components running imported driver code compiled from C, which can fault, hang or be compromised at any moment while holding a live channel.

Five requirements, in the order they constrain the design:

  • No syscall on the hot path. Submission is stores to memory the producer already has mapped. Nothing else.
  • No copies. Buffers are transferred by ownership, not duplicated.
  • ABI-stable across trust and language boundaries. The peer may be an imported driver built against the shim in section 14 of the architecture document, a WASM component, or code from a toolchain you do not control. Everything shared is #[repr(C)], fixed-width, and version-stamped.
  • A dead peer must not corrupt or hang us. This single requirement eliminates more design options than the other four combined — most importantly, it forbids any lock in shared memory.
  • Bounded latency, not just high throughput. A design that is fast on average and occasionally stalls forfeits the determinism claim outright. p99 is the number this architecture is measured on; a good mean is not evidence of anything.
02

Memory layout

One channel is one contiguous shared mapping. The indirection between the index ring and the entry array is worth keeping from io_uring: it lets a producer prepare entries out of order and publish a batch with one store.

Channel layout — one shared mapping
offset    size   contents
------    ----   --------
0x0000    64     ChannelHeader   magic, abi_version, ring_size,
                                 sqe_off, cqe_off, epoch, capabilities
0x0040    64     ProducerCursor  head: AtomicU32          // own cache line
0x0080    64     ConsumerCursor  tail: AtomicU32, flags   // own cache line
0x00C0    4*N    SQ index ring   u32 slots, N a power of two
...       64*N   SQE array       64-byte entries, one cache line each
...       32*M   CQ ring         32-byte completions, inline
...       var    inline arena    optional, for payloads under ~256 bytes
The cursors get their own cache lines, and this is not a micro-optimization. If head and tail share a line, every producer store invalidates the consumer's copy and every consumer store invalidates the producer's. Measured cost of getting this wrong is roughly 100–150 cycles per operation — enough to turn a 30 ns submission into a 200 ns one. If your first benchmark comes in five times slower than expected, this is the reason, essentially every time.

Ring sizes are powers of two so index computation is cursor & mask rather than a division. Cursors are free-running and allowed to wrap: occupancy is head.wrapping_sub(tail), which stays correct across the wrap because unsigned arithmetic wraps the same way. Never store a separate count — a count is a second piece of state that can disagree with the cursors.

03

The cursor protocol

Two things must be exactly right: the memory ordering that publishes an entry, and the mechanism that decides whether to wake the peer.

Producer — the entire hot path
let head = self.head.load(Ordering::Relaxed);   // we are the only writer
let tail = self.tail.load(Ordering::Acquire);   // peer publishes with Release

if head.wrapping_sub(tail) == self.mask + 1 {
    return Err(Full);                          // never block, never spin here
}

self.sqe[(head & self.mask) as usize].write(entry);      // 1. payload
self.head.store(head.wrapping_add(1), Ordering::Release);  // 2. publish

// 3. the two ends run Dekker here: we store head then load flags,
//    the peer stores flags then loads head. Store-load is the one
//    reordering TSO permits, and Release/Acquire do not forbid it.
//    Without this fence both sides see nothing and the peer sleeps
//    holding work. RFC 0020.
fence(Ordering::SeqCst);

// 4. wake the peer only if it told us it is going to sleep
if self.flags.load(Ordering::Acquire) & NEED_WAKEUP != 0 {
    self.doorbell();
}

The Release store is the whole correctness argument: it guarantees the entry write is visible before the cursor advance that exposes it. Paired with the consumer's Acquire load, that is a complete happens-before edge. On x86-64 both compile to plain mov with only a compiler barrier; on ARM64 they become stlr and ldar. Using Relaxed here works on x86 and fails on ARM, which is the worst possible failure mode — it will pass every test you run on your laptop.

Notification suppression

Waking a peer costs one to two microseconds — three orders of magnitude more than a submission. So the consumer publishes its intent instead:

  • While actively draining the ring, the consumer clears NEED_WAKEUP. Producers see this and skip the doorbell entirely.
  • Before sleeping, the consumer sets NEED_WAKEUP, then re-checks the ring once more before actually sleeping — this second check closes the race where a producer published between the drain and the flag write.
  • The consumer's flag write is a SeqCst read-modify-write and the producer has the fence above. Both halves are needed, and the second check does not substitute for them: it closes the case where the consumer's flag write is late, and not the case where the consumer's ring read is early. RFC 0020, which was written because this list said the second check was enough.

Under load this drives doorbell count to zero and the channel becomes pure polling. Under idle it costs exactly one doorbell to restart. The same idea is proven in io_uring's polled mode and in virtio's event-index mechanism; it is not novel and it should not be reinvented.

On a deadline-class core the consumer should never sleep at all. It parks with user-level monitor-and-wait — UMONITOR/UMWAIT on x86, WFE on ARM — armed on the cursor's own address, so the core drops to low power but wakes on the store itself. No interrupt, no scheduler, no jitter tail. This is one of the seven capabilities named in section 13 of the architecture document, and it is the easiest of them to adopt: the instructions have shipped for years and are almost entirely unused.

The doorbell itself

Suppression minimizes how often you ring. User interrupts change what a ring costs, and the two compose — this is not a choice between them.

Conventionally a doorbell is an inter-processor interrupt: the kernel is entered, a target is resolved, an interrupt is delivered, the receiving side traps back out. One to two microseconds, and worse, a variable one to two microseconds. With user-level interrupt delivery the sending core writes a user-interrupt target register and the receiving thread's handler runs without any kernel transition on either side — roughly a hundred cycles, and far more importantly a bounded hundred cycles.

  • It collapses the gap between the polled and blocked paths. Today the design pushes hard toward polling because waking is catastrophic; when a wake costs a hundred cycles, an idle consumer can block and stay responsive, which recovers the energy that constant polling burns.
  • It removes the last kernel entry from the notification path, so a fully idle channel and a fully saturated one have the same cost structure.
  • The suppression protocol above stays exactly as written. NEED_WAKEUP still governs whether to signal; only the cost of signalling changes.
Keep the fallback. User interrupts are recent and unevenly available. Abstract the doorbell behind one function with three implementations — user interrupt, kernel IPI, pure polling — selected at channel creation from what the hardware actually reports. Then measure all three. The delta between them is one of the cleanest results this system can produce, because nobody has published it for a general-purpose IPC path.
04

Buffer ownership, and the ergonomics answer

Section 11 of the architecture document lists ergonomics as the risk most likely to sink bet 02: completion-based I/O with borrowed buffers is genuinely harder to write than a blocking read, and if developers respond by wrapping everything in a blocking shim, the entire performance argument evaporates. This is the section that answers it.

Registration, once

A process registers a memory region once and receives a BufferSetId. The IOMMU mapping is established at that moment and never touched again. Individual operations then reference (buf_set, index, offset, len) — sixteen bytes, no per-operation pinning, no page-table work, no validation beyond a bounds check against a size the kernel already knows.

And on capable hardware, not even once

Registration exists to solve a problem that newer silicon removes. With IOMMU shared virtual memory — process address space identifiers, address translation services, page request interfaces — a device walks the process's own page tables and takes ordinary page faults when it touches something not resident. There is nothing to pin and nothing to register, because the device shares the address space rather than being handed a window onto it.

  • The SQE's buffer triple becomes a plain virtual address in the submitting process's own address space, with the PASID carried by the channel rather than the entry.
  • Long-lived buffer pools stop being a requirement, which removes the most awkward constraint the ownership API imposes on callers — a caller can submit from an ordinary allocation.
  • Memory that is never touched is never faulted in, so a large sparse buffer costs what it uses rather than what it spans.
Both paths ship, and the difference is the result. Registration remains the fallback for devices without translation services, and it is what section 13's efficiency claim is measured against: pinned-and-registered versus shared-virtual, same workload, same device class, reporting page-fault cost and tail latency alongside throughput. Device-side faulting is not free — a fault on the device path is far more expensive than one on the CPU path, and a design that faults in the middle of a deadline-critical operation has traded a known cost for an unknown one. Which path wins, and under what access pattern, is an open question worth answering properly rather than assuming.
Make the buffer set an object, not a table entry. A registered region is more useful as a first-class capability object — one that can be granted, cloned copy-on-write, resized and shared, with rights that only ever narrow — than as an index into a per-process array. Fuchsia's memory objects are the worked example, and the shape fits this system exactly: a buffer set becomes something the capability system already knows how to route, revoke and account for, rather than a second bookkeeping mechanism running alongside it.

Ownership transfer, enforced by the compiler

The failure mode of every completion-based API is the same: a future is dropped while the kernel still holds a pointer into its buffer, and the kernel writes into memory that has been freed or reused. Reference counting hides it; the type system can eliminate it.

The API shape that makes the bug unrepresentable
/// A buffer whose address is stable for as long as it is owned.
pub unsafe trait StableBuffer { fn parts(&self) -> (BufSet, u32, u32); }

/// Proof that an operation is in flight. Holds the buffer hostage.
pub struct Submitted<B: StableBuffer> { buf: B, token: u64 }

impl Ring {
    // buf is MOVED in — the caller no longer has it
    pub fn submit<B: StableBuffer>(&self, op: Op, buf: B) -> Submitted<B>;

    // the ONLY way to get it back is to await the completion
    pub async fn complete<B>(&self, s: Submitted<B>) -> (Result<u32>, B);
}

// Dropping a Submitted without completing it does not free the buffer.
// It submits a cancel and moves ownership to the runtime's graveyard,
// which releases it when the cancellation completes.
impl<B> Drop for Submitted<B> { /* ... */ }

Because the buffer is moved into Submitted and only returned by complete, there is no way to hold a reference to it while the operation is in flight. Cancellation safety, the notoriously subtle part of async I/O, becomes a property of ownership rather than a rule in the documentation. This pattern is well established in Rust's io_uring bindings and is the correct thing to borrow wholesale.

The Drop above is the shape and not what was built. It needs a runtime that can submit a cancel from inside a destructor and hold the buffer until the cancel completes, and no such runtime exists yet; RFC 0024 makes the drop a bomb instead — a component that abandons a buffer the device holds ends, and the frame's teardown revokes its sets and tears down its IOMMU domain so the transfer faults rather than lands. When the user-level runtime arrives, the graveyard here supersedes the bomb for components that run on it.

Then hide it. The ownership API is the foundation, not the interface. Above it, ship an ordinary-looking async API — read, write, send — that owns its buffers internally and batches submissions transparently. Developers should be able to write ordinary code and get batched zero-copy behavior without knowing the word "ring". If reaching the fast path requires understanding this section, bet 02 has already failed.
05

Entry formats

Sixty-four bytes for a submission, one cache line exactly. Thirty-two for a completion, so two share a line.

OffTypeFieldPurpose

1u8flagsLINK (next entry waits on this one), DRAIN, FIXED_BUF, NO_CQE for fire-and-forget.

The completion carries user_data, a result, flags, an ext word — and a completion timestamp taken by the service at the moment the work finished. That last field costs eight bytes and gives you per-operation deadline adherence across the whole system for free, with no instrumentation build and no sampling profiler. For a system whose entire proposition is measurable determinism, it pays for itself immediately.

Chaining

The LINK flag makes the next entry depend on this one's success. Read, then transform, then hand to the compositor becomes one batch, published with one cursor store and at most one doorbell. This is the mechanism that makes the "fewer than ten boundary crossings per frame" target in section 10 achievable rather than aspirational — without chaining, every dependency becomes a round trip.

06

Surviving a dead peer

The peer on the other end of a channel is frequently an isolated component built around imported C driver source. It can fault, hang, be restarted underneath you, or be compromised through a bug in code neither you nor its vendor has audited for this environment. The rule is simple to state and it constrains everything: shared memory is untrusted input, always.

This is a sharper threat than it looks, and it is the reason section 14's import strategy is safe. Imported drivers hold no ambient authority and are confined by the IOMMU — but they still sit at one end of a live shared mapping, which is the one channel confinement cannot police. The rules below are what make that mapping safe to expose, and they are therefore load-bearing for the architecture's central safety claim, not merely defensive hygiene.
  • No locks in the shared region. None. A peer that dies holding a mutex deadlocks the survivor permanently, and there is no safe recovery. Single-producer/single-consumer rings need no locks at all; that is the main reason to prefer one ring per client over one shared ring.
  • Validate every cursor on every read. If head.wrapping_sub(tail) > ring_size, the channel is corrupt. Tear it down, log it, do not attempt repair, and never panic — a peer must not be able to halt you by writing a bad integer.
  • Never dereference anything from shared memory. Indices only, bounds-checked against sizes held in your own private memory. A pointer in a shared region is an arbitrary-write primitive handed to the other side.
  • Read each field exactly once. Copy the entry out before validating it. Validating in place and then reading again lets the peer change the value between the two — the classic time-of-check/time-of-use bug, and it appears in almost every first implementation.
  • Stamp an epoch in the header. A restarted peer increments it; a mismatch means every outstanding token is stale and must be discarded rather than matched against the new peer's completions.

When you do need many producers

Inside a single trust domain a multi-producer ring is fine, using per-slot sequence numbers rather than a lock:

Lock-free MPSC claim — only within one trust domain
let pos  = self.enqueue_pos.fetch_add(1, Ordering::Relaxed);
let slot = &self.slots[(pos & self.mask) as usize];

// wait for the slot's turn — no lock, no ABA
while slot.seq.load(Ordering::Acquire) != pos { core::hint::spin_loop(); }

slot.write(entry);
slot.seq.store(pos.wrapping_add(1), Ordering::Release);
Note the limit. A producer that dies between claiming pos and storing seq stalls that slot forever. That is acceptable among threads of one process, which fail together anyway. It is not acceptable across a trust boundary — and an imported driver component is a trust boundary. There, one SPSC ring per client, always, with the number of clients bounded at channel-creation time.

Part II

The compositor

07

Scene deltas, not pixels

The compositor owns one retained scene graph covering every window on the machine. Nobody hands it pixels and nobody hands it command buffers. It receives edits to the scene it already holds.

Who sends those edits changed. Under the interface thesis in section 15 of the architecture document, applications do not author scene nodes at all — they declare a semantic structure, and the projection layer in part III derives scene deltas from it. Everything in this part is unchanged by that: the compositor is agnostic about whether a delta was authored by hand or projected, and it must stay that way, because the projection layer is the newest and least settled piece of the system while this pipeline is the most load-bearing. Read part II as the rendering target and part III as its principal client.

The arithmetic is the entire argument. A 4K frame is about 33 MB. A typical UI frame changes somewhere between five and fifty nodes — a caret moves, a value updates, a panel slides. Fifty deltas is roughly two kilobytes. That is a factor of ten thousand, and it is why the copy count in section 02 of the architecture document collapses rather than merely shrinking.

Node kinds

Deliberately few. Every additional node kind is a new shader path and a new source of pipeline stalls.

  • Transform — an affine matrix applied to a subtree.
  • Clip — a path restricting a subtree.
  • Layer — opacity and blend mode; forces an intermediate target only when it genuinely must.
  • Draw — a filled or stroked path, a glyph run, or an image.
  • Effect — blur, drop shadow, or a material, parameterized rather than open-ended.
  • Semantic — role, label, value, relations. Carried in the same tree, submitted in the same commit.
Accessibility lives in the scene graph from the first commit. It is one extra node kind now and an unshippable retrofit in three years, because by then thousands of drawing calls will exist with no semantic content attached and no way to infer it. This is the cheapest correct decision in the entire document.

The delta protocol

Carried on an ordinary ring, using the ordinary envelope from part I: CreateNode, SetTransform, SetPath, SetPaint, RemoveNode, then Commit. The commit carries a frame token and the deadline it was scheduled against, and it is atomic — the compositor applies every delta in a commit or none of them. A half-applied frame is a torn frame, and there is no recovery from it that the user will not see.

08

The GPU pipeline

Four stages, of which only the first touches the CPU. This is the shape Vello demonstrates and the reason section 05's CPU raster segment disappears entirely rather than merely getting faster.

1Encode. Walk the dirty subtrees and flatten them into a linear encoding of paths, transforms and paints. The only CPU stage, and it touches changed nodes only.CPU · ~0.3 ms
2Coarse raster. A compute shader bins path segments into 16×16 tiles. Prefix-scan computes per-tile counts and offsets in parallel, which is the trick that removes the inherently sequential part of rasterization.GPU · ~0.5 ms
3Fine raster. One workgroup per tile computes exact coverage per pixel and composites in linear space. Blur, shadow and material effects are stages in this same pass, not separate render targets.GPU · ~1.2 ms
4Present. Write the swapchain image, or hand the surface straight to the display controller when one surface covers the screen and no composition is required.GPU · ~0.1 ms

Text, honestly

Pure path rendering for all text is the elegant answer and the wrong one. Body text at 14 px has too many small paths and the per-glyph overhead dominates. The pragmatic split: shaping on the CPU, cached by (string, font, size, features) since the same runs recur constantly; a coverage atlas for small static text; GPU path rendering for large, animated, or transformed text where the atlas would need constant regeneration and resolution independence actually matters. Say this out loud in the design rather than discovering it after committing to one path.

Explicit synchronization only

Timeline semaphores throughout, never implicit driver synchronization. The application signals value N when its deltas are ready; the compositor waits N and signals M when composited; the present engine waits M. Implicit sync means the driver inserts waits you did not ask for and cannot see, which is survivable on a desktop and disqualifying on a machine whose selling point is a bounded frame time.

09

The latency chain

Section 05 of the architecture document sets the budget. This is the mechanism that meets it, step by step, with the two moves that recover the most time marked.

1The input driver timestamps the event from the hardware clock at interrupt time — not when userspace gets around to reading it.t = 0
2The compositor computes backwards from the next scanout. It knows the display's timing and its own rolling p99 GPU cost, so it sets the application's deadline at T_scanout − gpu_p99 − margin and wakes it exactly then. The app is not asked to render as early as possible; it is asked to render as late as is safe.recovers ~1 frame
3The application wakes under the deadline scheduler class, produces deltas, commits.+3 ms budget
4The compositor applies the commit atomically and encodes the dirty subtrees.+0.3 ms
5Late-latch. Immediately before GPU submit, pointer and stylus position are re-read and patched directly into the relevant transform nodes. Cursor-tracking content is therefore one whole frame fresher than the rest of the scene, which is precisely the content whose lag people notice.recovers ~1 frame
6GPU pipeline stages 2 through 4 run.+1.8 ms
7Scanout, with variable refresh so the frame is displayed when it is ready rather than at a fixed cadence.+2 ms
Frame pacing is where most implementations quietly lose their advantage. Rendering immediately after the previous present maximizes throughput and maximizes latency — the finished frame then waits in a queue for the display. Submitting as late as the p99 estimate safely allows is the single highest-return change in the whole pipeline, and it costs nothing but bookkeeping.

Counting the boundary crossings

Section 10 asks for fewer than ten per frame. Walking the chain above: the application writes deltas into shared memory, which is zero. Its commit suppresses the doorbell because the compositor is actively polling, which is zero. The compositor reads the deltas from shared memory, zero. Its GPU submission goes through its own ring to the driver component, zero — followed by one MMIO doorbell write, which is not a system call. Present is one more. Two hardware writes and no system calls per frame is the steady state. The target has margin in it.

10

Degrading instead of missing

This section inverts a habit every desktop compositor has, and it is where the interface layer stops being a rendering exercise and becomes a determinism claim.

A conventional compositor that will not finish in time renders late. That is the wrong trade in both directions, for two separate reasons:

  • A late frame is worse than a simplified one. Missing the scanout means the previous frame is shown again and the new one lands a full period later — a visible hitch. Dropping a blur to a cheaper approximation for one frame is, in practice, invisible. The system is optimizing the wrong variable when it protects quality at the cost of timing.
  • The compositor must not be able to perturb anything else with a deadline. It shares memory bandwidth with every other consumer on the machine, and bandwidth — not compute — is what they genuinely contend for. A compositor that can starve a deadline-class workload by drawing an expensive frame has made every other latency guarantee in the system conditional.

Two mechanisms, both of which must exist from the first version, because retrofitting either means rewriting the scheduler integration:

  • Effect level-of-detail against a per-frame budget. Each effect node declares a cost estimate and a cheaper fallback. When the running estimate exceeds the remaining budget, the compositor downgrades effects in a fixed, deterministic priority order — deterministic so degradation is reproducible under test rather than a source of visual bugs nobody can reproduce twice.
  • The compositor is the lowest-ranked deadline task on the machine, and its GPU submissions are bandwidth-capped. Not merely a lower priority — an explicit cap, so a pathological frame cannot transiently starve anything above it. The compositor is a real-time task and it is the least important one.
The measurable form. Take any deadline-class workload the system can already hold — a low-latency audio round trip, a control loop, an inference job under a QoS class — and establish its baseline distribution. Then run it again with the compositor deliberately overloaded: a pathological scene, every effect enabled, at the highest refresh the display will accept. The workload's p99.9 must not move. If it moves, the isolation is decorative and the architecture's determinism claim is conditional on nobody drawing anything interesting.

This is a cheap experiment and an unusually informative one, because it fails loudly. Most systems have never run it, which is why most systems have a compositor that can ruin a real-time workload and no documentation admitting so.

Part III

The semantic layer

11

The semantic model

Section 15 of the architecture document argues the thesis: the application declares a semantic structure, the system owns it, and pixels are one projection of it. This part is how that gets built. The structure has to be precise enough to implement, small enough that developers will adopt it, and expressive enough that they do not immediately escape from it — and those three pull against each other, which is the research problem.

What a node holds
struct Node {
    id:        NodeId,          // stable, author-assigned, survives redesign
    role:      Role,            // a small CLOSED vocabulary
    content:   Content,         // text | value | media | none
    state:     StateSet,        // enabled, selected, expanded, busy, invalid
    relations: SmallVec<Relation>, // labelled_by, controls, owns, flows_to
    intent:    Option<CapRef>,  // a capability — NOT a callback
    layout:    Constraints,     // intrinsic size, flex — NEVER coordinates
    style:     TokenSet,        // semantic tokens — NEVER colour values
}

Four of those fields carry a rule that is load-bearing rather than stylistic.

  • Intent is a capability reference, not a callback. The most consequential line in the struct. A callback is opaque — you can invoke it and you can learn nothing else about it. A capability reference means the system knows what a control does: it can describe the action to a screen reader without the author writing a label, check whether a caller is permitted to invoke it, log it, and — because storage is versioned under bet 03 — undo it. This is the join that makes agent control an authorized capability invocation rather than screen-scraping with extra steps, and it wires the interface thesis directly into bet 04.
  • Layout is constraints, never coordinates. The instant an application says x = 340 the structure stops being projectable to anything but the display it was written for. Constraint-based layout is the price of multi-projection, and there is no partial version of this rule — one escape hatch and every projection except the local one silently degrades.
  • Style is semantic tokens, never values. emphasis, danger, surface-2 — resolved at projection time against the active theme and the display's actual characteristics. This is the mechanism behind section 06's claim in the architecture document that a theme reaches applications its author never saw; without it that claim is decoration.
  • Identity is stable and author-assigned. A visual redesign must not change node identity. This is what makes automation and tests non-brittle, and it is also what lets the projection layer diff cheaply instead of re-deriving.

Transport and ownership

Carried on an ordinary ring using part I's envelope: DeclareNode, SetState, SetContent, SetRelations, Remove, Commit — atomic per commit, deadline-stamped, exactly like the scene protocol in section 07. Nothing new is needed at the transport layer, which is a good sign for the design.

The inversion in one sentence: the system owns the tree and the application holds a handle to it. Today applications own their interface and grudgingly export a shadow of it on request. That reversal is the entire thesis, and everything else in this part is consequence.

The concession that decides adoption. Developers want to write immediate-mode code — rebuild the whole tree every frame, because it is dramatically easier to reason about than manual delta bookkeeping. The system wants retained, for the reasons in section 07. Resolve it in the client library: run reconciliation locally against the previous tree and emit only the differences. Developers write immediate-mode; the wire carries deltas. This is the same failure mode as the ring ergonomics problem in section 04, and it has the same answer — if using the model correctly requires understanding the model, it will not be used correctly.
12

Projection

Projection turns the semantic tree into whatever a particular consumer needs. For the display that means scene deltas, which is where part II picks up.

1Resolve. Style tokens against the active theme and the display's real characteristics — density, colour gamut, HDR capability, reduced-motion preference. A token becomes a value only here, and never in the application.~0.05 ms
2Solve. Layout from constraints and the viewport. The expensive stage, and the one that must be incremental or the whole pillar fails.~0.2 ms
3Emit. Produce scene deltas. Part II's retained scene graph is the output of this stage rather than something an application authored.~0.1 ms
4Part II section 08 runs unchanged from here — encode, coarse raster, fine raster, present.~1.8 ms
Incrementality is the entire engineering risk in this part. If a delta touching five semantic nodes triggers a full layout solve, the section 05 budget is gone and the simpler design wins outright. Work must be proportional to the change, not to the tree — which means dirty-tracking through the constraint graph, and constraints scoped tightly enough that a local change cannot cascade globally. Expect this to be where a negative result comes from, if one comes.

The budget follows directly from the architecture document: the application gets 3 ms, so reconciliation plus all three projection stages must fit comfortably inside a fraction of it. Target under 0.5 ms for a typical delta on a realistic tree. That is the number the pillar is measured against.

The payoff: many projections, one structure

ProjectionWhat it producesApplication code required

The system runs projection, not the application. Applications supply custom rendering for canvas nodes only — which is the necessary escape hatch, and therefore the subject of the next section.

13

The hard cases

Three of them, stated with their failure conditions, because this pillar is the least settled part of the system and pretending otherwise would make the rest of these documents less trustworthy.

Can a canvas participate?

This is the case that sank every predecessor. An audio timeline or a 3D viewport renders its own pixels and cannot be expressed in any reasonable node vocabulary. If such a node becomes an opaque rectangle, then every projection except the local display goes blind exactly where the application's real work happens — and the thesis is true only for toolbars and dialogs.

The design: a canvas node declares both its custom rendering and a semantic model of its content. A timeline declares tracks, clips, time ranges and the current selection. A viewport declares objects, camera and selection. The pixels stay bespoke; the content stays addressable and manipulable.

The test, stated so it can fail: can an agent select the clip between 4.2 s and 6.8 s on track 3, and can a screen reader describe it, without either one seeing a single pixel? If yes, the thesis holds through the hard case. If no, canvas is an opaque box and the pillar is only partly true — which is worth knowing early rather than at the end.

There is an incentive problem underneath the technical one, and it deserves stating plainly: this asks developers to declare structure they do not currently declare. The honest pitch is that they get automation, accessibility, testing, remote projection and agent support in exchange, where today each of those is a separate integration they must write and maintain. That trade is only real if declaring the semantic model is less work than the five integrations it replaces. Whether it is, is a usability question rather than a technical one, and it should be tested against real developers early — the answer determines whether the pillar is adoptable at all.

Does the indirection cost the budget?

The falsifiable claim. Measure semantic-delta-to-photon against directly-authored-scene-to-photon, same content, same machine, same display. They must be within noise. If projection costs a millisecond, section 05's budget is spent on indirection, the simpler design wins on its merits, and the pillar should be abandoned rather than defended. Run this comparison as early as there is anything to run it on.

Is the vocabulary the right size?

Too small and applications escape into canvas, which voids the thesis. Too large and it becomes another sprawling markup vocabulary whose meanings are ambiguous in practice — the failure that overtook accessibility annotation on the web.

The approach: start deliberately small, and treat every escape into canvas as a bug report about the vocabulary rather than as an application's choice. That converts a vague design question into a measurable one — canvas-escape rate across a corpus of real applications — which is an unusually concrete metric for interface research and worth reporting whatever it says.

What would falsify the pillar

  • Projection cannot be made incremental enough. The latency budget is lost and the indirection is not worth its cost.
  • Canvas-escape rate stays high. The semantics do not cover the work real applications actually do, and the model describes only their edges.
  • Developers will not declare structure without enforcement. The deepest risk, and the one that killed every predecessor. F's enforcement is structural — do not declare it and nothing renders — but canvas is a legitimate loophole, and if enough developers reach for it the loophole eats the thesis from inside. That is precisely the mechanism by which advisory semantics rotted everywhere else, arriving by a different route.
Sequence this pillar behind the others. Parts I and II are load-bearing and comparatively well understood; this part is neither. Build the compositor so it neither knows nor cares whether a delta was authored by hand or projected — then the semantic layer can be developed, measured, and if necessary abandoned, without taking the rendering pipeline down with it.

14

Environment and repository

Phase 00 runs on QEMU on bare metal, with no hypervisor and no partitioning. Those come later and would only obstruct the work here. Boot with UEFI through an existing bootloader — writing your own costs two weeks and teaches nothing that matters to this design. A modern bootloader hands over a memory map, a framebuffer, higher-half mapping and secondary-CPU startup, all of which you would otherwise write twice.

Repository layout
fastpath/
├── abi/          // the ONLY crate crossing a trust boundary.
│                // #[repr(C)], fixed-width, no generics, no Drop,
│                // version-stamped. Review every change to it.
├── ring/         // the protocol from part I. no_std, used by both
│                // kernel and userspace — one implementation, not two.
├── kernel/
│   └── src/
│       ├── arch/x86_64/  // gdt, idt, apic, paging, context switch
│       ├── mm/           // frame allocator, page tables, address spaces
│       ├── cap/          // capability table, derivation tree, revocation
│       ├── chan/         // ring setup, doorbell routing
│       └── sched/        // round-robin now, EDF at phase 01
├── user/init/    // the first user process
├── xtask/        // cargo xtask run | test | debug — no Makefiles
└── tests/        // integration tests driven through QEMU
Isolating abi/ as its own crate is a structural decision, not tidiness. It is the only code whose layout is load-bearing across a boundary you do not control. Keeping it small and separate means every change to it is visible in review, and it gives you one obvious place to put the version check that stops a mismatched peer from being interpreted as corruption.

Two decisions worth making now rather than later

  • Make all kernel state per-CPU from the very first allocation, behind a PerCpu<T> abstraction, even while only one core is running. Retrofitting per-CPU sharding onto global state is one of the genuinely miserable refactors, and this system's whole premise is that cores do not share.
  • Bring up the second core early — around M3 — but not before. Early enough that no single-core assumption calcifies; late enough that you are not debugging SMP and paging simultaneously.
15

The milestone ladder

Seven milestones. Each has a done-criterion that is a test rather than a feeling, and every one of those tests belongs in CI the day it first passes.

M0

It boots, it says so, and it is already deterministic

Custom target JSON, bootloader handoff, serial output on COM1, panic handler that prints something useful. Plus the one thing that cannot be added later: the determinism substrate. Time, randomness and every ordering decision reach the system only through an injectable Env capability, never from an instruction — with a build-failing lint on the forbidden calls, and coverage instrumentation added while the kernel is small enough for it to be trivial.

Done when cargo xtask run prints a banner in QEMU and exits with status 0, driven by -device isa-debug-exit so the kernel can set its own exit code and a real integration test can assert on it — and when a seed plus a commit hash reproduces a run byte for byte.
2–4 days · the substrate is irreversible — see Proving Ground section 04
M1

Memory

Parse the bootloader's memory map into a physical frame allocator. Take ownership of the page tables rather than inheriting them — higher-half kernel with a direct physical map.

Done when a stress test allocates and maps a thousand random frames, writes and verifies a pattern, unmaps and frees, ten times over — and the allocator's free count at the end is bit-identical to the start.
~1 week
M2

Interrupts and time

GDT, IDT, exception handlers with a register dump you will read hundreds of times. Local APIC, TSC-deadline timer, calibrated against a known reference.

Done when a 1 kHz timer runs for 60 seconds and you have a jitter histogram with p99 under 5000 ns. This is the first real-time measurement in the project and it exists in week three — from here on, every milestone reports it, and a regression fails the build.
~1 week · the most important milestone on this list
M3

User space, and a second core

User page tables, the ring-3 transition, a syscall entry used strictly for channel setup and never on a hot path. Load a flat binary from a boot module. Start the application processors.

Done when a user process runs on core 1, faults deliberately, and is killed cleanly while core 0 keeps its timer jitter inside the M2 bound throughout.
1–2 weeks
M4

Capabilities

A per-process table of typed slots — Untyped, Frame, AddressSpace, Channel, Endpoint, Irq. Derive a weaker capability, copy one, and revoke recursively through a derivation tree.

Done when the negative test suite passes: a process cannot name a capability it was not given, cannot forge a handle, cannot use a revoked handle, cannot exceed granted rights, and cannot make the kernel panic by trying. These tests are the phase-00 exit criterion from section 09 of the architecture document, written as code.
1–2 weeks
M5

The first ring

Everything in part I: the layout, the cursor protocol with correct acquire/release ordering, notification suppression. Exactly two opcodes to start — NOP and WRITE_SERIAL.

Done when one million NOPs submitted in batches of 32 report under 50 ns per operation, and the number is recorded in CI as a regression gate. If it comes in above 200 ns, re-read section 02 before changing anything else.
~2 weeks
M6

Phase 00 complete

Nothing new — this milestone is composition and proof.

Done when a capability-restricted user process communicates with the kernel entirely through a ring, touches nothing it was not handed, and the whole suite runs under one command in CI with timer jitter and ring throughput recorded as gates on every commit.
total: 7–10 weeks · matches the 0.5–1.5 person-year figure in section 09
16

Tooling, and what not to build

Worth setting up on day one

  • cargo xtask for all orchestration. Build, run, debug and test as Rust code rather than a Makefile. It stays readable at the point where the build genuinely gets complicated, which it will.
  • QEMU's debug-exit device, so the kernel returns a real exit status and integration tests are ordinary cargo test rather than log-scraping.
  • A committed .gdbinit plus qemu -s -S. Symbolized breakpoints in kernel code from M0 turns most triage from guesswork into stepping.
  • qemu -d int,cpu_reset in your notes. The first triple fault arrives during M1 and this is how you find it.
  • The jitter histogram and ring benchmark in CI from M2 and M5. This is the habit that makes section 10's metrics real. Numbers that are not gated regress silently, and on a project whose entire claim is determinism, a silent latency regression is the failure that matters.

Explicitly not in phase 00

  • No filesystem. The object store is phase 02 and it is a different kind of problem. Boot modules are enough to load a binary.
  • No general heap. A bump allocator plus a slab for fixed-size kernel objects. A real allocator now is speculative work against requirements you do not have yet.
  • No imported drivers, and no shim. Bare QEMU with virtio. The kernel-API shim in architecture section 14 brings a large body of foreign C into the system, and introducing it before capabilities and rings are solid means debugging two unfamiliar systems through each other.
  • No drivers beyond serial and the timer. Not even virtio — that is M-something in phase 01, once the ring it would be built on actually exists.
  • No graphics. The compositor in part II is phase 03. Attempting it before rings and deadlines are solid produces a demo you have to throw away.
The through-line: phase 00 exists to prove exactly two propositions — that isolation holds under adversarial use, and that the ring is genuinely faster than a system call. Everything in the ladder above serves one of those two. Anything that serves neither is phase 01 or later, however tempting it looks at the time.
Reference implementations worth reading before starting, in roughly this order: Asterinas for the framekernel partition in practice · seL4 for capability derivation and revocation done correctly · the io_uring documentation for the cursor and suppression protocol · virtio's event-index mechanism for the same idea arrived at independently · Vello for the compute rasterization pipeline · Jailhouse for how small a partitioning hypervisor is allowed to be.
