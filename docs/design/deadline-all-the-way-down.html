Fourth companion · the resource subsystems

Deadline All the Way Down

The five subsystems that phases 01 through 06 rest on and that the earlier documents named without designing: CPU time, memory, storage, network and accelerators. They are treated together because they are the same problem — a contended physical resource allocated against a deadline — and because giving each its own ad-hoc policy is precisely the mistake that makes conventional systems miss deadlines through a resource nobody was watching.

01

One discipline, five resources

A conventional system gives every resource its own unrelated policy: a fair-share scheduler for CPU, an elevator for storage, queueing disciplines for network, an approximation of least-recently-used for memory, and nothing whatsoever for accelerators. None of those policies knows the others exist.

The consequence is the failure mode the architecture document keeps describing from different angles: a task with a deadline misses it because of contention on a resource that no policy was watching. Section 10 of the implementation companion caps the compositor's memory bandwidth for exactly this reason — and as written that cap is a one-off patch on a general problem.

The design One admission-and-accounting discipline, parameterized per resource. Every request carries a class and a deadline — the submission entry already has both fields. Every resource has a scheduler that is a policy plugged into one framework, and all five share a view of what is due and when. The compositor's bandwidth cap then stops being a special case and becomes an instance of a mechanism that also governs storage garbage collection, key-value cache residency and inference admission.

The four classes

  • Hard. The deadline must be met. Admission-controlled — a reservation is granted only if the resource can prove it is schedulable, and refused otherwise. This is what makes the word "deadline" mean something rather than function as a hint.
  • Soft. A deadline exists and is honoured on a best-effort basis; missing it degrades quality rather than correctness. The compositor lives here, which is why section 10 of the implementation companion has it degrade rather than run late.
  • Batch. Throughput matters, latency does not. Storage compaction, indexing, background inference.
  • Idle. Runs only on resources nothing else wants.

02

CPU time, and the runtimes above it

The scheduler's primitive is not a weight. It is the triple (class, deadline, energy cost), and every design decision below follows from refusing to collapse that into a single number the way a priority does.

Admission control is the load-bearing part

A component asking for the hard class states a period and a worst-case execution budget. The scheduler runs a schedulability test against existing reservations and either grants or refuses. A refused reservation is an error the caller must handle, exactly like a failed allocation.

This is unusual enough to be worth defending. Every system that treats deadlines as hints ends up with deadlines that are not met, because nothing ever refuses work. Admission control converts a soft promise into an arithmetic one: if the test passes, the deadline is met by construction; if it fails, you learn at reservation time rather than during a take.

Heterogeneous cores, and why slack decides placement

Each core class carries a measured performance and energy model — frequency to throughput to power — calibrated at first boot rather than assumed. Placement is then a function of slack, not priority:

  • A task with little slack relative to its budget goes to a fast core, because nothing else meets the deadline.
  • A task with generous slack goes to the slowest core that still meets its deadline, because that is almost always the lowest-energy choice. Racing to idle on a fast core loses to finishing just in time on an efficient one for most work.

Priority-based schedulers cannot express this, because priority conflates urgency with importance and slack is neither. Energy-aware extensions bolted onto fair-share schedulers approximate it and miss, which is one of the section 13 capability gaps this design exists to close.

Deadline propagation across the rings

This is why the submission entry has a deadline field. When a task blocks on a completion from another component, that component's work inherits the caller's deadline. Without inheritance you get priority inversion at the I/O layer: a hard-class task waits behind batch work in a storage queue and misses its deadline through a resource it never contended for directly. The deadline travels with the request, through every ring it crosses, and each resource scheduler orders by it.

User-level runtimes

The kernel does not schedule tasks. It allocates cores to runtimes, and a runtime schedules its own work inside that allocation with no kernel involvement — the reason async work never crosses a boundary. The kernel preempts only at allocation boundaries and on reservation expiry, and it notifies a runtime when it is about to lose a core so the runtime can park cleanly rather than being interrupted mid-task.

The concurrency model above that is structured: a task owns its children, cancellation propagates down, and a cancelled task's in-flight ring operations are cancelled through the ownership mechanism in section 04 of the implementation companion rather than abandoned. Cancellation and buffer ownership are the same problem and get one answer.

Policy is pluggable, and verified

The policy interface is small — select a core for a task, enqueue, dispatch, handle a tick, handle a block or wake — and a policy is loaded as sandboxed, verified code with a bounded execution guarantee and the ability to be ejected. This is the mechanism sched_ext proved viable, made native rather than an add-on. The hard class is not delegated: admission control and earliest-deadline-first dispatch stay in the frame, and a policy governs everything below.

03

Memory: three resources, not one

Every system conflates three genuinely different resources under one word, and only the first is usually managed at all.

  • Capacity — how many bytes. The one everybody accounts for.
  • Bandwidth — how fast they can be reached. The actually-contended resource on a modern machine, and unmanaged nearly everywhere.
  • Tier — where they live: on-package, on-board, across an interconnect. Latencies differ by an order of magnitude and the cost model is nothing like the uniform-access assumption most allocators carry.

The mechanics

Physical memory is a buddy allocator with per-CPU free lists and huge pages by default, because translation misses are a measurable part of the budget this system claims. The frame owns the page tables; a component receives an address space and memory objects as capabilities, per the object model in section 04 of the implementation companion, and cannot name memory it was not granted.

Accounting is hierarchical and follows the capability routing tree: a component's quota is bounded by what was routed to it, and its children's quotas sum within its own. Allocation failure is therefore local and deterministic — the component that exceeded its budget gets the error. There is no global out-of-memory killer choosing a victim, which is both a correctness property and a precondition for the deterministic simulation in the testing companion, since a global killer is a system-wide nondeterministic event.

Tiering, measured rather than guessed

Placement is a function of access frequency and latency sensitivity, both observed: access-bit sampling and hardware event sampling give a real access profile rather than an inference from allocation order. Migration between tiers is asynchronous, rate-limited, and itself a batch-class consumer of memory bandwidth — so the tiering machinery cannot cause the deadline miss it exists to prevent.

Bandwidth as a first-class reservation Modern processors can partition memory bandwidth between groups of cores. Deadline-class components receive a bandwidth reservation the same way they receive a CPU reservation, and batch work is throttled to fit around it. This is what turns the compositor cap in section 10 of the implementation companion from a hand-placed limit into an instance of a general mechanism — and it is the only honest way to make the concurrent-inference claim, since inference is a bandwidth hog and audio is a bandwidth-sensitive deadline task competing for the same controller.

One consequence worth stating plainly: model weights and key-value cache are not special. They are memory objects with a tier policy and a bandwidth class, managed by this subsystem. Section 06 adds nothing to that beyond admission.

04

Storage: the object store, concretely

Bet 03 asserts a content-addressed immutable store. This is the design behind the assertion.

Format

A blob is content plus its hash. An object is a blob whose content references other blobs by hash. A root is a single hash from which the entire system state is reachable, so a system generation is one hash and a rollback is a root swap.

Large objects are split by content-defined chunking — a rolling hash chooses boundaries, so an edit near the start of a large file does not re-chunk everything after it. This is what makes deduplication and delta transfer work in practice rather than in principle, and it is the difference between a store that shares data between generations and one that quietly stores twenty copies of a slightly edited file.

The zoned mapping, which is the elegant part

Blobs are append-only. Zones are append-only. They are the same shape. A zone is filled sequentially with blobs and sealed. When a zone's live fraction falls below a threshold, its surviving blobs are copied forward and the zone is reset. That is the garbage collector — and it is the same operation the device's own flash translation layer would otherwise perform underneath, without knowing which data is live. Doing it once, with knowledge, instead of twice, blindly, is where the write-amplification claim in section 13 comes from. A conventional filesystem cannot make this claim because it promises random overwrite and must lie to the device to keep that promise.

Collection

Reference counting is the wrong mechanism — it costs on every write and handles the reachability question badly. Instead: mark from the set of live roots, sweep zones by live fraction. The mark is incremental and generational, and the sweep is a batch-class consumer of storage bandwidth under section 01's discipline, so collection can never starve a deadline-class read. Roots are pinned explicitly, which is also how snapshot retention is expressed — keeping a generation means keeping its root.

Naming and query

Directories are a view, not the ground truth. The index maps paths, metadata and semantic attributes to blob hashes, and it is an embedded log-structured store rather than a separate service — queries are a local call, not a round trip. Search becomes a query over the index instead of a walk over a tree, which is the claim in the technology table.

Durability, and the read path

The durability primitive is not a flush of dirty pages. It is publish this root: write the blobs, then write the root. Atomicity is free because a root is a single write, and a crash mid-publish leaves the previous root intact with some unreferenced blobs the next collection reclaims.

Reads resolve a hash to a zone and offset through the index, then direct-memory-access straight into the caller's registered buffer. There is no page cache holding a second copy, which removes both the copy and the memory the copy occupied.

Where this design is genuinely bad. Content addressing punishes small random writes to large mutable objects — a database file, a virtual machine image, a video project's scratch file. Every write re-chunks and re-hashes a region and produces a new root. The mitigation is a second object kind: a mutable extent, copy-on-write at coarse granularity, content-addressed only at snapshot boundaries. This is a real complication rather than an elegant unification, and pretending the pure model covers every workload would be the kind of overclaim the comparison document warns about.
05

Network

The subsystem with no prior coverage in any document, and the one where the right move is mostly to import.

What is written, and what is not

Per the principle in section 14 of the architecture document — write what you research, import what you do not — the split is unusually clean here. The datapath is written; the protocol logic is imported. Congestion control and protocol correctness are decades of accumulated work in which F has no claim and no interest; the zero-copy, user-interrupt-delivered path from device queue to application memory is exactly where the claim lives.

  • Queues are mapped into the owning component, through virtual functions or direct queue-pair assignment, so the datapath involves no kernel and no copy.
  • Receive: headers go to the protocol stack, payload lands by direct memory access in the application's registered buffer — or, on hardware with shared virtual memory, straight into ordinary application memory with no registration at all.
  • Transmit: the buffer is owned by the ring until completion, using the same ownership discipline as every other operation. Networking gets no bespoke lifetime rules.
  • Protocol: take an existing stack. Prefer QUIC as the primary transport — it is user-space-native, which fits this architecture rather than fighting it, and it carries streams and cancellation semantics that map onto rings far better than a byte-stream socket does.

Authority and contention

There is no ambient network authority. A component holds a capability naming specific endpoints or a port range; there is no "the network" to open. And bandwidth is a reservation under section 01's discipline, so a batch transfer cannot starve a deadline-class flow — the same mechanism, a fourth time.

State the claim narrowly. The measurable assertion is packets per second per core, and joules per packet, against a tuned Linux using its own zero-copy receive path — not "our networking is faster." Throughput of a borrowed TCP implementation says nothing about F, and claiming it would poison the numbers that do.
06

Accelerators

Section 13 of the architecture document says mainstream systems treat an accelerator as a device file with one tenant, no quality of service, no preemption and no accounting. This is what replacing that looks like, and it is mostly an application of the preceding four sections rather than new machinery.

  • Submission carries a class and a deadline, like every other request, and admission control applies: an inference job asking for hard-class latency is granted a reservation or refused.
  • Memory is the real contention, and section 03 already owns it. Weights and key-value cache are memory objects with tier policies. Cache residency is a paging decision, which is an operating system's oldest competence applied to a new consumer.
  • Weights come from the object store, content-addressed — so ten components using the same model share one physical copy, mapped rather than loaded. That is a concrete, easily measured win over the per-process copy every current runtime makes, and it is the cheapest result in this document to demonstrate.
Preemption is the honest problem. Many accelerators cannot be preempted mid-kernel, so a long submission blocks the queue no matter what the scheduler wants. The mitigation is to bound work per submission — split large kernels so the scheduling quantum is a submission rather than a job — which costs some throughput and requires cooperation from the runtime producing the work. Where a closed vendor runtime will not cooperate, the quantum is whatever that runtime chooses, and every number measured through it is bounded by it. Report that alongside the result rather than quietly averaging it in.
07

Boot and the component topology

A capability-routed component system needs a defined origin, and no document so far provides one.

  • Measured boot to a root of trust, then the frame, which holds every capability that exists and has granted none.
  • The frame starts one component: the assembler, handing it the root of the system generation — a single hash. Everything else follows from that hash, which is what makes a generation reproducible and a rollback a boot-time argument rather than a recovery procedure.
  • The assembler instantiates the component topology described by the generation, routing capabilities declaratively as it goes. Nothing acquires authority by asking; everything receives it by being placed in the topology.
  • Drivers bind by matching declared device properties, and a driver that fails to start leaves its subtree unstarted rather than failing the boot. The topology is therefore partially available by design, and the shell must be built to expect that rather than assume completeness.
The property this buys: boot is a pure function of one hash. The same root produces the same topology, which is what allows the deterministic simulator to start a run from a known system state rather than from whatever the last test left behind — and what makes "roll back one generation" a complete, verified statement rather than a hope about what got restored.

09

Where this is weakest

  • Admission control is an API burden. Every hard-class reservation can be refused, and callers must have something sensible to do about it. Systems that make failure impossible are pleasanter to program until the moment they silently miss a deadline instead — but the burden is real and the ergonomics need the same attention the ring API got, or developers will simply request the soft class for everything and the discipline evaporates.
  • The unified discipline is unproven at five resources. Deadline scheduling of CPU is well understood. Applying one admission framework across memory bandwidth, storage, network and accelerators simultaneously is the interesting part and also the part with no precedent — the interactions between reservations on different resources may not compose as cleanly as this document assumes.
  • Deadline propagation can be gamed. If inheriting a caller's deadline promotes work, a component that always claims urgency wins. Bounding inheritance by the caller's own reservation is the answer, and it needs designing before it is implemented rather than after the first starvation bug.
  • The storage design has a workload it is bad at, and mutable extents are a patch rather than a resolution. Measure that case early and honestly — it is the one a skeptic will reach for first.
  • Everything here is design, not measurement. Every number these subsystems are meant to produce is currently zero. The build order stands: this document exists so phases 01 through 06 have something to build against, not because designing further ahead than that would be wise.
