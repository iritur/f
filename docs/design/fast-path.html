Reference architecture · systems research

The Fast Path

Four goals — blazingly fast, technologically current, effective everywhere, beautiful and fully customizable — do not automatically coexist. Speed usually costs safety. Customization usually costs stability. Beauty usually costs latency. This document picks the small set of architectural invariants that make all four fall out of the design instead of fighting each other, names the concrete technology for each layer, and is honest about which parts ship today and which are a bet.

01

The thesis in one paragraph

A modern OS is not slow because its instructions are slow. It is slow because it crosses protection boundaries and copies memory thousands of times a second, schedules threads that immediately block, and paints pixels through five layers of indirection. So the whole design reduces to four invariants: no boundary crossing on the hot path (shared-memory rings instead of syscalls), no copies (buffers are handed over, never duplicated), no ambient authority (capabilities, so isolation is free rather than a tax), and no mutable global state (content-addressed, versioned storage, so customization can never corrupt the system). Speed, security and customizability then stop being trade-offs against each other — they become the same property viewed from three angles. Beauty is the fifth invariant, and it is really a latency budget.

03

Five load-bearing bets

Everything else is detail. If any one of these five is wrong, the project is wrong.

Bet 01 — kernel shape

Framekernel, not microkernel or monolith

Run everything in one address space for monolithic speed, but use Rust's ownership model to partition the kernel into a small privileged frame — the only code allowed unsafe — and unprivileged services above it. Microkernel-grade isolation reasoning without paying microkernel IPC.

What could break it Soundness of the frame is a proof obligation, not a compiler guarantee. Get the frame's API wrong and the entire safety argument collapses silently.
Bet 02 — the I/O primitive

One primitive: the shared-memory ring

Not files, not sockets, not ioctls. Every service — storage, network, graphics, timers, IPC, process control — is a submission and completion ring pair in shared memory, addressed by capability. Batched, asynchronous, zero-copy, uniform. io_uring generalized from an I/O accelerator into the entire system interface.

What could break it Rings are hard to make ergonomic. If writing against one feels worse than a blocking read, nobody writes native apps.
Bet 03 — state model

Content-addressed and immutable, top to bottom

No mutable filesystem as the primary abstraction. A Merkle-DAG blob store with copy-on-write views, and the entire system configuration as a pure function of a declarative expression. Snapshots, atomic upgrade, instant rollback, reproducible builds and free undo become one mechanism instead of six features.

What could break it Write amplification and garbage collection. And every existing tool assumes mutable paths.
Bet 04 — authority

Capabilities, with no root and no global namespace

A process can only touch what it was handed. There is no path to escalate because there is nothing to escalate to. Sandboxing stops being a feature bolted on top and becomes the default state of the machine, at no runtime cost.

What could break it Usability. Capability systems fail when granting authority is inconvenient — the file picker has to be the grant mechanism, invisibly.
Bet 05 — the display

One GPU-driven scene graph for the whole machine

Applications submit scene deltas, not pixels. The compositor holds a single retained scene for every window on the system and resolves it in one GPU pass, vector-native and resolution-independent. Blur, refraction, real material shading and 120 Hz animation become nearly free because they are one shader, not thirty composited surfaces.

What could break it It requires a new toolkit. Every legacy app that submits pixel buffers falls back to the slow path and looks foreign next to native ones.

05

Beauty is a latency budget

"Beautiful" is not a font choice. What people perceive as quality in an interface is overwhelmingly the delay between moving their hand and the screen agreeing, plus the absence of jitter. Fix the latency and even a plain interface feels expensive; miss it and no amount of blur and shadow rescues the machine. So set a hard budget and architect backwards from it.

Four mechanisms buy the difference:

  • Timestamp input at the driver and predict forward. The compositor knows when the next scanout is and renders for that instant, not for when the event arrived. This alone removes a full frame.
  • Rasterize vectors on the GPU. Compute-shader path rendering — the approach Vello demonstrates, using prefix-scan to parallelize work that is normally sequential — makes resolution independence and real-time effects cheap and deletes the CPU raster segment entirely.
  • Never copy a frame. One retained scene graph, damage-tracked, explicit GPU synchronization through timeline semaphores, direct scanout when a surface is fullscreen.
  • Give the UI a deadline, not a priority. The scheduler needs earliest-deadline-first classes so the compositor and audio threads structurally cannot be preempted into a missed frame. Real-time capability is a UI feature.
Where this is genuinely hard: a 9 ms budget gives an app 3 ms to produce a scene delta. Any garbage-collected language with a stop-the-world pause above 1 ms is disqualified from the UI thread. That is the real reason the base system has no GC.
06

Customization without fragility

"Fully customizable" normally means "eventually broken." Users change something, it interacts badly, the machine stops booting — so vendors respond by locking everything down. The way out is to make experimentation structurally non-destructive. Three mechanisms, each for a different scope:

  • Configuration is a declarative expression and the system is its output. The Nix and Guix model. The entire machine — packages, services, dotfiles, kernel parameters — is a pure function of one versioned expression. Every change produces a new generation; the previous one is still on disk, one boot entry away. You can change anything because you can undo everything.
  • Everything above the kernel frame is a swappable typed component. Interfaces defined in WIT, implemented as WebAssembly components. Replace the compositor, the shell, the indexer or the window manager without recompiling the system — and without those components gaining any authority they were not granted.
  • Policy is sandboxed, verified code injected into the system. This is the mechanism sched_ext proved works: let people write the actual scheduling algorithm, load it into the running kernel, verify it terminates, and stay able to eject it when it misbehaves. Apply the same pattern to I/O policy, cache policy, power policy and security policy. It is the difference between a configuration flag and genuine programmability.

Visual customization follows the same logic. A system-wide typed design-token layer in the compositor — color, spacing, radius, motion, material, type scale — means a theme restyles every native application including ones its author never saw, and cannot break layout because the tokens are typed and range-checked.

And the deepest form of customizability: every UI action is a call on the same capability API that automation uses. The graphical shell is one client of the system, not a privileged one. That makes the machine scriptable by construction rather than by scraping.

07

Future-oriented means AI-native, structurally

An OS designed now that treats accelerated inference as an application concern will be legacy on arrival. Being AI-native is not a chat window in the corner — it is four specific pieces of systems work:

  • The NPU is a scheduled resource with QoS, not a device file. Current on-device engines are built for isolated inferences and degrade badly under concurrent, conflicting requests across CPU, integrated GPU and NPU. The OS is the only component that can see all three, so heterogeneous co-scheduling belongs there.
  • KV cache is a memory tier the OS manages. Inference progress is tightly coupled to accelerator memory consumption; placement, eviction and reuse across processes is a paging problem, and paging is an operating system's core competence. Model weights come from the content-addressed store — deduplicated across every app, mapped rather than copied.
  • Semantic index as a first-class, capability-gated service. The user's data indexed locally and privately, queryable by meaning, granted per-app like any other capability. This is what makes local assistance useful rather than a demo.
  • Agents are principals in the capability model. An autonomous agent gets a scoped, revocable, auditable capability set — and because storage is immutable and versioned, every action it takes is inspectable and reversible for free. This is the strongest argument for bets 03 and 04: the immutable, capability-based design that looks academic today is exactly what makes an agentic machine safe to hand real authority.

One more detail worth knowing: energy-aware scheduling tuned for browser workloads actively harms inference, parking CPUs at low frequencies during model execution and degrading both latency and efficiency. Power management has to become workload-aware — again an OS-level concern, not an app-level one.

Build order

Ordered because it genuinely is a sequence — each phase is unusable until the previous one exists. Effort figures are person-years for a competent team, and assume you are not also inventing new research. They are the honest reason most OS projects should narrow their scope before writing any code.

11

Where this most likely fails

Worth stating plainly, because the failure modes of new operating systems are extremely well documented and almost identical every time.

The ecosystem wall
This is what kills OS projects, not technical difficulty. Fuchsia had a decade and a very large team, shipped a real microkernel, a real component framework and a real Linux compatibility layer — and never found a use case that generated developer interest. Technical excellence does not produce an ecosystem. Decide who the first thousand users are and what they cannot currently do, before phase 00.
Drivers
Modern GPUs, Wi-Fi and power management represent tens of thousands of person-years of accumulated vendor work. The viable answers are: target one machine exactly, the way Asahi did; stay on virtio under a hypervisor; or shim an existing driver ecosystem. Writing them yourself is not on the list.
The UI toolkit tax
Phase 03 is larger than phases 00 through 02 combined, and it is entirely unglamorous: text shaping, bidirectional layout, input methods, accessibility, color management, printing. Redox needed years of work before a desktop environment could be ported to it. Budget for this or the OS stays a terminal demo forever.
Rings are ergonomically hostile
Completion-based asynchronous I/O with borrowed buffers is genuinely harder to write against than a blocking read, and Rust's ownership model makes it harder still. If the ergonomic layer is not excellent, developers wrap everything in a blocking shim and the entire performance argument quietly evaporates.
Immutability meets reality
Content-addressed storage fights write-heavy workloads, garbage collection becomes a real engineering problem, and every existing tool assumes mutable paths. The mutable-path compatibility view is not optional and is not cheap.
Betting on immature dependencies
CHERI is still an evaluation platform. Vello is alpha. WASI 0.3 is months old. Each is the right long-term call and each can slip by years. Every bet needs a documented fallback that is merely good rather than exceptional.
12

The honest recommendation

Do not build a general-purpose desktop OS. Build this architecture for one workload where current systems visibly fail — a low-latency creative workstation, a robotics or edge controller, a confidential-computing guest, an agent execution host — and let generality arrive later if it earns its way in. That is what every successful new OS actually did: seL4 through certification-critical embedded, Fuchsia through appliances, Asahi through exactly one laptop.

The architecture here does not get weaker when the target narrows. The framekernel, the universal ring, the immutable store, the capability model and the GPU-driven compositor are all more defensible on a focused machine than a general one — because a focused machine lets you choose the hardware, skip the compatibility layer, and spend the entire budget on the fast path. Then widen.

13

The research target

Everything above is the general architecture. This section commits it — not to a product, but to a research vehicle, which changes what counts as success.

The ecosystem wall in section 11 is a product problem. Research systems are judged on defensible measured claims rather than on users: Exokernel, Barrelfish, Arrakis, Singularity and Theseus between them had approximately no users and changed how a generation of systems were built. That removes the constraint that kills most clean-slate work. It does not lower the bar — it moves it onto measurement, where a claim without a named baseline, a published workload and a reproduction command is not a result.

Thesis Mainstream operating systems are built on a hardware model that stopped being accurate around 2015. They assume uniform cores, one flat memory tier, devices that need the kernel to mediate every access, and accelerators that are just files. A decade of silicon capability — user-level interrupts, device-side address translation, memory tiering across CXL, zoned storage, on-package matrix engines — is either unused or retrofitted into abstractions that predate it. This system is the argument that designing for the current machine, rather than adapting to it, is worth a large constant factor in both speed and energy.

Speed and efficiency are therefore not separate promises. They are the predicted consequences of the thesis, which is a considerably stronger position than claiming both directly.

What makes it evidence rather than a demo

  • The baseline must be a tuned Linux, not a default one. Compared against a stock configuration, every number here is meaningless. The comparison is Linux with io_uring, with a sched_ext policy chosen for the workload, with huge pages, with the relevant device features enabled — configured by someone trying to win. Beating a strawman is the most common way systems research becomes worthless, and it is entirely self-inflicted.
  • Report instructions and energy, not only time. Nanoseconds per operation conflate algorithmic wins with clock speed. Instructions retired per operation, joules per operation and resident bytes per unit of work are the numbers that survive a hardware change — and given the efficiency claim, energy is not optional.
  • p99 and p99.9, never means. An average hides exactly the behavior the architecture exists to fix.
  • One command reproduces every claim. If a third party cannot re-run it, it is an anecdote.
  • Whole-system deterministic simulation, and it has to be designed in from the first commit. The architecture already supplies what a simulator needs, as a side effect of decisions made for other reasons: every interaction is a ring, so there is one interception point rather than thousands; no ambient authority, so no hidden channels; drivers in user space, so a modelled device is a component substitution; content-addressed storage, so whole-system state comparison is a hash comparison. Given a determinism substrate — time, randomness and every ordering decision behind an injectable capability — a seed and a commit hash reproduce any run byte for byte. This is the one property on this list that cannot be retrofitted, which is precisely why no mainstream kernel has it. Proving Ground sets out the substrate and the six layers built on it.
  • Measurement is a system service, not a build configuration. Every component exposes a live, hierarchical, queryable tree of its own state and counters — readable without a debugger, without a special build, and without stopping the system. Fuchsia's diagnostics layer is the model worth copying here. This reads like tooling and gets deferred for that reason, which is a mistake in a system whose output is measurements: completions already carry timestamps, and this is the mechanism that turns them into evidence rather than into a profiling exercise somebody has to set up by hand.
The question that replaces "who are your first thousand users": can you state a small number of claims, each with a named baseline and a number, that a competent skeptic could try to refute and fail? Three defended claims beat twelve asserted ones, and the failure mode of ambitious systems work is almost always the second.

Importing drivers without importing Linux

No Linux runs anywhere in this system. Nothing boots it, nothing runs beside it, and there is no compatibility partition. What gets imported is driver source, compiled against a shim into this system's own isolated components. The distinction matters and it is not a technicality: the imported code runs under this kernel's memory model, this kernel's scheduler and this kernel's capability rules, or it does not run.

Principle Import what you are not researching. Write what you are. If a claim depends on a code path, that path must be yours — importing Linux's block layer to make a storage-efficiency argument would mean importing the thing being measured.

Split the graphics driver before deciding anything about it

"Import the GPU driver" hides two very different problems, and conflating them makes the task look harder than it is. The kernel-mode half is entangled with its host kernel and is what a shim exists to carry. The user-mode half — Mesa — is the majority of the code and is already portable, because it has been made to run on several operating systems and reaches the kernel through a narrow, per-driver interface.

So the target is Mesa plus a DRM-shaped kernel interface, not a port of any vendor's kernel driver. Fuchsia arrived at exactly this decomposition independently — its graphics architecture is a GPU-specific library loaded into each application's address space, plus a system driver that owns the hardware. That split is the right one to copy even though, as below, its drivers are not.

Three ways to import, in order of preference

  • Source-level KPI shim. Implement enough of Linux's internal kernel API — allocation, locking, work queues, completions, the DMA and PCI interfaces, the device model, the DRM core — that unmodified driver sources compile against this kernel. Upstream fixes keep applying, because the source is unmodified. The cost is that you are implementing an API surface you do not control and which grows; tracking it is continuous work rather than a one-time port.
  • Library-kernel import. Compile Linux as a library behind a small host interface and run it as a component. Broader coverage, since you get whole subsystems rather than individual drivers — but you also inherit Linux's internal architecture wholesale, which means running a second scheduler and memory model inside your own. Acceptable for a subsystem you have no claims about; corrosive if it spreads.
  • Anykernel-style import. Drivers from a source already factored for out-of-kernel use. The cleanest engineering of the three and the smallest hardware coverage, which for a research vehicle may be the wrong trade.

The container the imported code goes in

Choosing what to import settles half the question. The other half is what it runs inside, and here there is a design worth taking wholesale rather than deriving.

Fuchsia's second-generation driver framework treats a driver as an ordinary component: it receives an incoming namespace of explicitly routed capabilities, speaks a typed protocol rather than calling into kernel internals, and carries a declared restart-on-crash policy so a fault takes down one driver host instead of the machine. That is precisely the arrangement section 08 specifies, already worked out and shipping. Linux drivers assume the opposite of all three — kernel context, ambient authority, and that a fault is terminal — which is exactly the gap a shim has to close.

Two properties of that container matter more than they first appear:

  • The boundary is a protocol, not a kernel API. A typed protocol surface is far smaller and far more stable than the internal-kernel-API surface a shim otherwise has to chase forever. The shim's job becomes bridging one driver's expectations to that protocol, rather than reimplementing an ever-growing slice of another kernel.
  • Authority is routed declaratively, and can therefore be checked. Capabilities are not passed by hand at runtime; they are declared in the component topology and resolved when the system image is assembled. That means the question what can this component reach? has a static answer, computed from the configuration rather than discovered by audit. For imported code nobody has reviewed for this environment, a mechanically checkable bound on reachable authority is worth more than any amount of code reading — and it composes directly with bet 03, since routing is simply more of the same declarative expression that builds the rest of the system.
Take the container, not the contents. Fuchsia's driver inventory cannot replace Linux's here, for three reasons and the second is decisive: its coverage was scoped to a narrow device range; its graphics architecture supports only unified-memory devices, with discrete-memory GPUs explicitly an unported aspiration — so for a workstation with a discrete card it supplies nothing at all; and the project is now in maintenance, which is the wrong risk profile for the one component deliberately chosen as not a research subject. Linux driver code will still have thousands of contributors in a decade. The synthesis is to put shimmed Linux drivers inside a Fuchsia-shaped container.

One further discipline worth importing with it: interface versioning. Defining a protocol is easy; evolving it without breaking independently updated components is the part that is actually hard, and Fuchsia's explicit availability annotations and compatibility testing are a solved answer to a problem this system will otherwise meet late and badly. Take the discipline, not the interface language — the ring protocols and the component interfaces both need it.

Why this strengthens the safety claim instead of weakening it

Imported driver code is C, and it would be the largest concentration of unsafe code in the system — a direct threat to the trusted-computing-base metric in section 10. The resolution is that it does not go in the trusted computing base at all.

  • Imported drivers run as isolated user-space components, IOMMU-confined and restartable — exactly the arrangement section 08 already specifies for native drivers. The isolation boundary is uniform; only the shim is per-driver.
  • An imported driver therefore holds no ambient authority and can address no memory it was not granted. A fault restarts one component. The unsafe-code metric counts the frame, not the drivers, and survives intact.
  • That arrangement is itself a publishable result: unmodified vendor driver code, running with no ambient authority, confined and restartable, with the cost of that confinement measured. Nobody has a good public number for what that isolation costs on a modern GPU.

The licence boundary is the isolation boundary

Imported Linux driver source is licensed under the GPL, and a component built from it is a derivative work. That is a constraint on the project's structure, not merely on its paperwork, and it is worth settling before the first import rather than after.

The resolution is unusually clean here, and it is a consequence of the architecture rather than a workaround. FreeBSD keeps its compatibility layer and the drivers built on it in a delimited part of its tree, and rests the separation on an in-kernel linking argument. F's imported drivers sit in separate address spaces, share no symbols, and communicate only over a ring — which is a far stronger separation than linking, and one that maps exactly onto the boundary the licence needs.

The consequence Keep the frame and all native components permissively licensed so the research is reusable, keep imported driver components in a delimited subtree under the terms their source requires, and let the ring be the only thing that crosses between them. The licence boundary and the isolation boundary then want to be the same boundary, and the architecture already draws it. This is an additional reason — independent of safety — to keep imported drivers out of the frame even where the confinement carries a measurable cost.
The honest risk. Graphics drivers make deep assumptions about their host kernel's memory management, scheduling and fence semantics, and they assume they are running in kernel context. FreeBSD's precedent is in-kernel; hosting the same drivers in an isolated user-space component is harder and is where this plan is most likely to need a fallback. Budget for the possibility that the GPU driver ends up inside the frame with a documented exception, and measure what that costs rather than hiding it.

The interface thesis

The second research pillar, and the one where the least has changed since 1984. Every mainstream system hands an application a rectangle and lets it draw. Everything the system subsequently wants to know about what is on that screen has to be recovered afterwards, by a separate mechanism, imperfectly.

Count the subsystems that exist purely to reconstruct information the application already had and threw away: the accessibility tree, the UI automation API, the theming engine, the test harness's selector language, the remote-display protocol, the screenshot-and-guess loop that agents use. Six mechanisms, six sets of bugs, six things that drift out of sync with the interface they describe — all because the drawing call discarded the meaning and kept only the pixels.

Thesis The application declares a semantic structure. The system owns it. Pixels are one projection of it, and not a privileged one.

What the structure actually holds

Precision matters here, because stated loosely this is a slogan rather than a design. Each node carries content (text, media, a value), a role (button, list, field, canvas), state (enabled, selected, expanded), relations to other nodes (labelled by, controls, flows to), and an intent — what activating it does, expressed as a capability invocation rather than a callback. Presentation is separate: layout constraints and style tokens, never pixel coordinates. The retained GPU scene graph described in the implementation companion is then derived from this structure rather than authored directly.

Subsystem todayUnder this model
Accessibility tree — separate, retrofitted, perpetually stale because nothing breaks when it is wrongThere is no separate tree to drift. The structure the screen reader consumes is the structure the pixels came from.
Automation and scripting — a second API, fragile selectors, breaks on redesignThe same nodes with the same stable identity that rendering used. Automation and display are two readers of one structure.
Theming — per-toolkit, cosmetic only, breaks layout when pushedStyle tokens resolved by the system at projection time, so a theme reaches applications its author never saw and cannot break a layout it does not control.
Testing — screenshot diffing and brittle queriesAssertions against the semantic tree, with node identity stable across visual change.
Remote display — encode and stream pixelsShip the structure; project it on the far side at the far side's resolution and refresh rate.
Agents — screenshots and coordinate guessingRead the structure, invoke the declared intent. Because intent is a capability call, every agent action is scoped, auditable and revocable — which is what section 07 was promising in the abstract.
Search and indexing — per-application, if at allThe semantic index reads live interface state as a matter of course.

Why this is research and not merely engineering

The open questions are genuine, and previous attempts failed on them rather than on effort:

  • What is the right node vocabulary? Too small and applications cannot express themselves, so they escape into opaque canvases. Too large and it becomes another sprawling markup vocabulary whose semantics are ambiguous in practice.
  • Can a custom canvas participate? This is the hard case and the one that has sunk every prior attempt. An audio timeline or a 3D viewport renders its own pixels — but it can still declare a semantic model of its content: clips, tracks, times, objects, selections. Whether that is expressive enough to be useful, and cheap enough to maintain, is the most interesting open question in this section.
  • What does the indirection cost? Deriving a scene graph rather than authoring one must not spend the latency budget from section 05. This is the falsifiable claim and it should be measured early, because a negative result here invalidates the pillar.

Honest prior art, and the distinguishing bet

This is not unprecedented. The web's document model with accessibility annotations is a semantic tree with a rendering projection, and it is a partial success at best. Model-view architectures, Morphic, and every accessibility API of the last thirty years have reached for the same idea.

They share one failure mode: the semantics were optional. An annotation that nothing depends on rots, because nothing visibly breaks when it is wrong. The distinguishing bet here is to make the semantic structure the only source of truth — if the tree is wrong, the pixels are wrong, immediately and visibly. Load-bearing structures do not drift, and that is the entire difference.

What a convincing demonstration looks like

  • One application, four projections — local display, a remote client at different density and refresh rate, a screen reader, and an agent driving it through declared intents — with no application code specific to any of them.
  • Latency parity with a directly authored scene graph, measured against the section 05 budget. The claim stands or falls here.
  • The hard case, done properly: a real-time timeline that renders custom pixels while remaining fully addressable, scriptable and describable. If the canvas degrades to an opaque box, the thesis is interesting but not proven.
