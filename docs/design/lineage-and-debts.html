Comparative analysis · second companion

Lineage and Debts

Twenty-six systems that tried something structurally new, what each one actually proved, what each one left unsolved — and where F stands against them. Written to be useful rather than flattering: the last two sections are the ones that matter, and they are the ones where F loses.

Companion to  The Fast Path Alongside  Ring, Scene, Boot · Deadline All the Way Down · Proving Ground Posture  synthesis, not superset
01

How to read this

The method behind F — take the strongest idea from each prior system and find a structure where they reinforce rather than fight — is sound, and it is how most durable systems work got done. But it needs one correction stated up front, because it is the specific way ambitious operating systems fail.

The correction F is a synthesis, not a superset. No system beats every predecessor on every axis, and the ones that set out to — Fuchsia most recently, with a decade and hundreds of engineers — end up beaten by their own scope. What F can defensibly claim is a specific combination nobody has assembled, plus roughly six things nobody has tried at all. That is a strong position. "Best at everything" is not a position; it is the absence of one.

So the comparison below has a fourth column that is often unflattering, and two closing sections that exist to keep the rest honest: what is genuinely new, which is shorter than it feels like it should be, and what F is permanently behind on, which is longer.

One note on fairness. Several systems here are twenty or forty years old and were solving their era's problems on their era's hardware. "What it left unsolved" is not a criticism of them — Exokernel had no IOMMU to work with, and Mach's IPC cost was a discovery nobody had made yet. The column records what the next system had to fix, which is how the field advances.

02

The lineage

Five inheritance streams. Almost nothing in F's architecture is unprecedented in isolation; the bet is on the combination and on the handful of joins between them.

Stream 01 — kernel structure
Asterinas framekernel partition
Singularity / Midori language-based isolation
Theseus intralingual design
Hubris all-Rust in production
Takes: one address space for speed, with the language rather than the MMU drawing the safety boundary, and the unsafe frame held to a few percent of the code.
Stream 02 — authority
seL4 capability derivation and revocation
KeyKOS / EROS pure capability systems
Genode recursive component composition
Fuchsia capabilities at product scale
Takes: no root, no global namespace, authority only by explicit grant — and Genode's insight that the same rule should apply recursively all the way down.
Stream 03 — the data path
Exokernel secure hardware multiplexing
Arrakis kernel as control plane only
Demikernel microsecond-scale datapath
io_uring the ring mechanics themselves
Takes: the kernel sets up and revokes the channel and is absent from it. This is the single largest borrowing in F, and Arrakis is its closest ancestor.
Stream 04 — state
Nix / Guix functional system configuration
git / Unison content addressing
Plan 9 uniform naming
Takes: the system as a pure function of a declarative expression, with immutability enforced by the storage layer rather than observed by convention.
Stream 05 — interface
NeWS send structure, not pixels
Fuchsia Scenic system-wide retained scene
Morphic live inspectable objects
DOM + ARIA semantics beside rendering
Takes: the display layer holds a structure rather than receiving images — and the correction that the structure must be load-bearing, not advisory.
03

Kernel architecture

SystemWhat it provedWhat it left unsolvedWhere F stands
Mach1985 That a kernel could be decomposed into servers at all — the idea that started the field. IPC so expensive that it discredited microkernels for two decades and drove the industry back to monoliths. F removes the boundary crossing rather than optimizing it. There is no fast IPC because on the hot path there is no IPC. Ahead
L4 · seL41993 · 2009 Microkernel IPC can approach the hardware floor, and a kernel can be fully machine-checked against its specification. Still the field's high-water mark for assurance. Verification cost roughly a person-decade for ten thousand lines and does not extend upward — everything built on seL4 is unverified. Address-space switches remain on every call. Borrows the authority model wholesale; declines the proof obligation, targeting the frame and protocols instead. Behind on assurance
Barrelfish2009 The multikernel: treat a many-core machine as a distributed system, share no kernel state, and scalability stops being a locking problem. Message passing everywhere is the wrong price when shared memory is cheap and coherent. Never met real workloads. Takes the no-shared-state rule as a design constraint, rejects the transport. Per-CPU from the first allocation; shared-memory rings instead of messages. Ahead
Singularity · Midori2004 · 2008 Software-isolated processes with contract-verified channels — isolation from types rather than hardware, with protocol conformance checked at compile time. Reportedly very fast. Required every line of code in one managed language, so no C and no imported drivers, ever. Garbage collection in the base system. Cancelled before shipping. Same thesis with Rust, so no GC — and F deliberately hosts untrusted native components, which Singularity structurally could not. Its verified channel contracts are the model for F's ring protocol checking. Ahead
Genode2008 Capability-based composition applied recursively — every component is itself a parent that can spawn and constrain children, across several kernel backends. Synchronous IPC-heavy design. Conventional interface layer. Small ecosystem despite genuine maturity. Rings replace synchronous IPC. But Genode's component model is more worked out than F's, and F should borrow from it rather than re-derive. Behind on component model
Fuchsia · Zircon2016 A capability-based, component-structured OS can ship on real consumer hardware with a real system compositor and run unmodified Linux binaries. Never found a use case that pulled developers in. Under the components, Zircon is a conventional syscall kernel — the novelty sits in the framework rather than the interface. F replaces the syscall interface itself, and being a research vehicle removes the ecosystem obligation that defeated Fuchsia. But it takes three separate mechanisms from that framework — declarative capability routing, the driver container, and live structured diagnostics — and none from the kernel. The driver inventory is the part that cannot be reused: its graphics stack supports only unified-memory devices. Behind on everything shipping-related
Redox2015 A Rust microkernel can be carried all the way to a usable desktop by a largely volunteer effort. Deliberately Unix-shaped. POSIX compatibility constrains the design, so it is a better-built instance of a known architecture rather than a new one. F is not Unix-shaped and carries no POSIX constraint. Behind on completeness
Asterinas2022 The framekernel works in practice: monolithic performance with the unsafe trusted base held near 14% of the code, and Linux ABI compatibility on top. Being Linux-shaped is the entire goal, so it inherits Linux's abstractions, syscall interface, I/O model and storage model along with its compatibility. F's closest kernel relative. Same structure, opposite goal — F takes the framekernel and rejects the ABI, the syscall interface and the I/O model. Divergent
Theseus2020 Intralingual design taken to its limit: no address spaces at all, runtime-composable cells, and state-spill elimination that makes live evolution tractable. Purity precludes hosting any untrusted or non-Rust code. Research scale, no serious hardware story. F is the compromised version — less elegant, but able to confine imported C drivers behind the IOMMU. Behind on purity
Hubris2021 An all-Rust kernel with a statically declared task set is not merely viable but preferable in production embedded systems. Static task set by design. Embedded scale. No dynamism, no general-purpose ambitions. F is dynamic and desktop-scale; it takes the discipline rather than the mechanism. Different scope
QNX1982 A microkernel RTOS can be commercially durable for forty years, with hard real-time guarantees and a partitioning hypervisor shipping in safety-critical products. Proprietary and POSIX-shaped. Architecturally conventional by current standards. F takes the seriousness about deadlines and the evidence that isolation and real-time coexist. Behind on field-proven reliability
04

The data path

This is where F's central claim lives, and where the lineage is most direct.

SystemWhat it provedWhat it left unsolvedWhere F stands
Exokernel1995 The kernel's only necessary job is secure multiplexing of hardware; abstractions belong in libraries the application chooses. Every application then had to implement its own operating system, which nobody wanted. 1990s hardware had no IOMMU, so isolation was expensive software work. Same division of labour, but the IOMMU now enforces it in hardware and the system ships good abstractions rather than requiring each app to invent them. Ahead
Arrakis2014 Kernel as control plane only: applications reach network and storage hardware directly through virtual functions, with order-of-magnitude latency gains. Covered network and storage alone. Depended on SR-IOV hardware that was then rare. Built on Barrelfish, so no path to a general system. F's closest philosophical ancestor. F generalizes the same thesis from two subsystems to every service, graphics and process control included. Ahead in scope
Demikernel2021 A portable library-OS datapath can hold microsecond-scale latency across heterogeneous kernel-bypass devices. Datapath only — no storage model, no interface layer, no system. Same philosophy applied to a whole system rather than one layer. Adjacent
io_uring2019 Shared-memory submission and completion rings with notification suppression make the syscall boundary nearly free at scale — in a production kernel, at enormous scale. An accelerator bolted beside the syscall interface, not a replacement for it. Ergonomically hostile enough that most software never adopts it. F makes the ring the only interface, adds a deadline field and completion timestamps, and treats the ergonomics as a first-class design problem rather than an afterthought. Ahead
UnikernelsMirageOS 2013 Specializing a single application into a single address space with no syscall boundary produces tiny, fast, minimal-attack-surface images. One application per image. No multi-tenancy, no interactive interface, difficult to debug and operate. F keeps the no-boundary property while remaining multi-tenant, which is the harder half. Ahead
05

State, naming and configuration

SystemWhat it provedWhat it left unsolvedWhere F stands
Plan 91992 One uniform naming mechanism plus per-process namespaces gives distribution, composition and sandboxing almost for free. Still the most elegant idea in operating systems. Synchronous file I/O as the universal interface cannot express asynchrony, batching or zero-copy — the uniformity is bought with performance. Same ambition, different universal primitive: the ring rather than the file. Uniformity that is asynchronous and zero-copy by construction. Ahead
Nix · Guix2003 · 2012 A whole system can be a pure function of a declarative expression, with atomic generations and one-boot rollback. Deep customization stops being dangerous. Built on top of a conventional POSIX filesystem, so immutability is a convention the kernel knows nothing about. Nothing at runtime participates. Evaluation is slow and the store grows without bound. The same model made native: the object store is the store, immutability is enforced by the storage layer, and the kernel is a participant rather than a bystander. Ahead
git · Unison2005 · 2019 Content addressing makes deduplication, verification and history free, and Unison showed it works for code rather than only for files. Neither is an operating system; neither confronts write amplification, garbage collection or hot-path latency. F carries content addressing into the storage layer and joins it to zoned devices — where the append-only shape stops being a cost and becomes a match. Ahead
NetBSD rump2007 Kernel drivers can be factored to run outside the kernel unmodified, given a small enough host interface. NetBSD's driver set, which is far narrower than Linux's on current hardware. F applies the same factoring to a Linux-sourced driver set through a source-level shim. Same technique
06

Interface architecture

The least-advanced area in the field, and consequently where F's second research pillar has the most room.

SystemWhat it provedWhat it left unsolvedWhere F stands
X111984 Network-transparent graphics, and that a display protocol can outlive four decades of hardware change. Pixels and events as the abstraction. Forty years of extensions, no security model, and semantics recoverable only by guessing. The design F exists to replace. Ahead
NeWS1986 The most under-remembered system here. Clients downloaded behaviour into a resolution-independent, PostScript-based display server, so interaction resolved locally with no round trip — vector-native and network-efficient decades before either was fashionable. Shipping a full programming language into the display server is a security and complexity disaster. Proprietary, and X was free. Same instinct — send structure, not images — with declarative semantics in place of downloadable code, which is what makes it safe to accept from an untrusted client. Ahead
MorphicSelf / Squeak, 1995 A live, uniformly inspectable, directly manipulable object world where the interface is editable while it runs. No separation between semantics and presentation, no security model, and performance that never reached production expectations. F takes liveness and uniform inspectability, and adds the separation Morphic lacked. Ahead
Oberon1987 An entire system — compiler, kernel, interface — small enough for one person to understand, with a genuinely app-less, command-oriented interaction model. Single user, no protection, effectively no concurrency, text-centric. F takes the app-less ambition into a protected, concurrent, graphical system. Ahead
Wayland2008 Fixing X11's security model and radically simplifying the protocol is possible and worth doing. Clients still submit pixel buffers; the compositor composites surfaces rather than owning a scene. No semantic layer at all, and protocol fragmentation has recreated much of X's extension sprawl. F's compositor owns one retained scene for the whole machine, and receives deltas rather than images. Ahead
Fuchsia Scenic2018 A system-wide retained scene graph works at product scale — the closest existing thing to F's compositor. Applications still author scene nodes directly. No semantic layer above the scene, so accessibility and automation remain separate retrofitted subsystems. F derives the scene from a semantic structure, which is the step Scenic did not take. Ahead
DOM + ARIA1998 · 2008 A semantic tree with a rendering projection, at planetary scale — by far the most widely deployed version of F's interface thesis. The semantics are advisory. Nothing visibly breaks when they are wrong, so they rot — which is the failure mode of every accessibility annotation system ever built. F's single distinguishing bet in this area: make the structure the only source of truth, so a wrong tree is immediately wrong pixels. Ahead if it holds
07

What is actually new

Stripping out everything inherited, seven things remain that no prior system has done or combined. This list is deliberately short, because a short defensible list is worth more than a long asserted one — and because every item here is a claim someone could try to refute.

  • The ring as the universal system interface. io_uring is an accelerator beside a syscall interface; Arrakis bypassed the kernel for network and storage only. Nobody has made one ring protocol the sole interface to every service — storage, network, graphics, timers, process control, IPC.
  • Deadlines and completion timestamps in the submission entry. Earliest-deadline-first ordering applied at the I/O layer system-wide, with every completion carrying when it actually happened. Eight bytes for whole-system latency accounting with no instrumentation build. No OS does this.
  • User-level interrupts as the doorbell for general IPC. The hardware exists and is essentially unused. Building an entire system interface on it, and publishing the measured difference against the interrupt path, is unclaimed ground.
  • Content-addressed storage meeting zoned devices with no translation layer. Nix's model and ZNS hardware are structurally the same shape — append-only, immutable, garbage-collected — and nobody has joined them. The write amplification that conventional stacks fight should simply not arise.
  • Semantics as the only source of truth for the interface. Every predecessor made them advisory and watched them rot. Making them load-bearing is the un-attempted version.
  • Untrusted imported drivers as confined ring peers, with the cost measured. FreeBSD runs foreign drivers in-kernel; nobody has published what it costs to run them isolated, IOMMU-confined and restartable, on modern graphics hardware.
  • An operating system architected so that whole-system deterministic simulation is tractable. The technique is proven elsewhere — FoundationDB on the order of a trillion simulated CPU-hours, TigerBeetle reproducing any bug exactly from a seed and a commit — and is almost never applied to operating systems, because kernels leak nondeterminism at thousands of unmarked places. F's ring interface, absence of ambient authority, user-space drivers and content-addressed state remove nearly all of them, not by design for testing but as a consequence of decisions made for speed and safety. The claim is that these are the same design pressure seen from three angles, and it is the only item on this list that must be built first or never.
Note what is not on this list. The framekernel, capabilities, kernel bypass, content addressing, declarative configuration, retained scene graphs, GPU vector rasterization and component models are all borrowed, and F should say so plainly in any writeup. Overclaiming on inherited ideas is how systems papers lose credibility, and the six items above are strong enough to stand without help.
08

Where F is behind, and will stay behind

The section that makes the previous one believable.

seL4 — assurance
seL4 is machine-checked against its specification. F will verify its frame and its protocols and will not verify the system. That gap is permanent unless someone funds a decade of proof work, and no amount of Rust closes it. When F claims safety it must say sound by construction in the following respects, never verified.
Fuchsia — reality
A decade, hundreds of engineers, shipping on consumer hardware, with a component framework and driver coverage F will not approach. F's advantage is that it does not need users; that is a change of subject, not a win.
Genode — component model
Recursive capability-based composition worked out far more thoroughly than anything in F's documents. F should be reading Genode rather than re-deriving it, and should expect to find its own model naive by comparison.
Serenity · Haiku — coherence
Complete, consistent, genuinely pleasant desktops built by small teams. Architecturally conservative and entirely finished, which is the opposite of F's position. Completeness is a real achievement and F currently has none of it.
Theseus — purity
F's framekernel is a compromise: it accepts imported C to get hardware support, and that compromise is exactly what Theseus refuses. Theseus is the more principled design and F should be honest that it traded principle for reach.
Linux — everything else
Thirty years of driver coverage, tooling, tuning and workload-specific optimization. F's baseline is a tuned Linux and F will lose to it on most axes that are not the six claims above. Any comparison that does not say so is not a comparison.
QNX — field evidence
Four decades of safety-critical deployment. F has a design document and a milestone ladder.
09

Nearest neighbours, in one line each

If someone asks what F is, these five comparisons answer faster than a description does.

Asterinasclosest kernel
The same framekernel structure aimed at the opposite goal. Asterinas exists to be Linux with a sound trusted base; F takes the structure and discards the ABI, the syscall interface and the I/O model.
Arrakisclosest thesis
The same argument — kernel as control plane, hardware reached directly — generalized from network and storage to every service in the system, on hardware that finally makes it routine.
seL4closest authority model
F's capability design is seL4's, minus the proof and minus the address-space switch. It inherits the rigour of the model and not the rigour of the method.
Fuchsiaclosest ambition
The same capability-and-component vision with a different interface primitive and none of the obligations. Fuchsia is what happens when this ambition meets a shipping deadline.
NeWSclosest interface instinct
Forty years earlier, the same refusal to send pixels — and the same recognition that the display layer should hold something structured. F sends declarative semantics where NeWS sent executable code, which is the difference between accepting it from an untrusted client and not.
