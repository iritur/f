Part I

The system

01

What F is, and what this book is not

true
State This chapter describes the project rather than the system, so nothing in it can be ahead of the code.

F is a research operating system built on the observation that mainstream systems assume a machine that stopped existing around 2015. Uniform cores, one flat tier of memory, devices that need the kernel to mediate every access, accelerators reached as if they were files. A decade of silicon capability — user-level interrupt delivery, device-side address translation, memory tiering, zoned storage, on-package matrix engines — is either unused or retrofitted into abstractions that predate it.

The thesis is that designing for the current machine rather than adapting to it is worth a large constant factor in both speed and energy. Speed and efficiency are therefore not two promises; they are the predicted consequence of one thesis, which is a stronger position to have to defend than two independent boasts.

What this book is not

It is not the argument. The argument is docs/design/fast-path.html, which states five load-bearing bets and is written for a reader who thinks they are wrong. This book assumes you have either read it or are willing to take the bets as given while you learn what they produced. If at any point you want to know why rather than what, the design documents are where why lives, and this book points at them rather than restating them.

It is also not the decision record. There are eighty-odd numbered RFCs in docs/rfc/, each one a decision and the conditions that would reverse it. This book cites them constantly and never restates them, because a decision recorded in two places is a decision that will eventually be recorded differently in two places.

The division of labour across the three books. Foundations — this one — explains the system to somebody who may change it. Applications explains how to write a component to somebody who takes the system as given. Evidence explains the apparatus that decides whether any of the claims are true, to somebody who does not believe them. A chapter belongs to the book whose reader needs it, which is why device drivers appear here as an architectural position and in Applications as a thing you write.

The three things to know before anything else

  • Determinism is not optional. Nothing observes time, randomness or ordering except through f_env::Env. The contract is that (seed, commit) reproduces a run byte for byte. This is the one property that cannot be retrofitted, and it is why whole-system simulation is possible here and not on Linux. RFC 0004.
  • The frame is three crates. abi, ring and kernel may use unsafe. Everything else in the workspace inherits unsafe_code = "forbid" and cannot opt out quietly. RFC 0001.
  • Claims gate the build. A number with no named baseline, no published workload and no one-command reproduction is an anecdote, and this repository will not publish one.

Where the project actually is

Milestone M0. The system boots, reports that it booted, and is already deterministic. The design documents are considerably ahead of the code, which is the intended order and is stated here so that nobody has to discover it. Work is organised into epochs E0 through E7 in TODO.md, each ending at a gate; E0 is ground truth and none of the later gates has been passed.

The honest summary of the risk is in docs/design/lineage-and-debts.html, which is the document that says what F owes to prior work and where it is behind and expects to stay behind. It is short, and a reader deciding whether to take this project seriously should read it before the architecture.

02

Getting started

runs
State Every command in this chapter executes today. If one does not, that is a bug in this chapter and not a feature that has not landed.

There are two routes and only one of them is supported. The supported one is the development container, whose single prerequisite is Docker; the other is a local toolchain pinned by rust-toolchain.toml plus qemu-system-x86_64 on your path. The container exists because the pinned toolchain is load-bearing — changing it invalidates every claim in the registry — and a container is the cheapest way to stop that happening by accident.

The supported route — Docker is the only prerequisite
# Windows
.\docker\dev.ps1 build
.\docker\dev.ps1 verify

# everywhere else
docker compose -f docker/compose.yaml run --rm dev cargo xtask verify

The -f docker/compose.yaml path is relative, so run it from the root of the checkout that git clone produced.

The one command

cargo xtask verify is the whole local loop: lint, then test, then boot, then mutate, failing cheapest first. A session runs it before a human is asked to look at anything, because the alternative is that the human is the test suite.

Healthy output ends with verify: all green and exit code 0. Anything else is a failure, and that includes a line beginning warning: — clippy runs with -D warnings, so there is no such thing as a warning you are allowed to leave. There is no partial credit and no summary line that says how many passed.

It has two gaps, stated rather than papered over. verify is local, so it cannot run the AArch64 tests or the litmus job — and those are exactly where the ring's memory ordering means anything, because total store order on x86 hides the entire class of bug the ring is exposed to. Those run in CI. A clean local verify is necessary and is not sufficient.

Seeing it boot

The boots, and what each one asserts
cargo xtask run          # boot in QEMU; the assertion is exit code 33
cargo xtask fault pf     # boot into a deliberate fault: pf ud df nx wx stack
cargo xtask user         # seven boots; a process breaks one rule each and is killed
cargo xtask cap          # eight boots; a process tries to escape its capabilities
cargo xtask cores        # two builds and four boots; what MAX_CPUS costs, and core counts
                         # that do and do not match the machine
cargo xtask mutate       # build the kernel wrong on purpose; the boot must go red
cargo xtask attest       # five boots; what is this machine running, and does it move

Read that list as the shape of the whole project rather than as a menu. Almost every verb boots the system more than once and requires the boots to disagree in a specific way. mutate is the clearest case: it builds the kernel with a deliberate defect and requires the boot to fail, then requires the same boot to succeed without it. A test suite that only ever goes green is measuring whether it runs, not whether it works.

There is no visual check anywhere in this project, because there is nothing to look at. The boot log is the equivalent: it is byte-identical for a given (seed, commit), so a diff of two logs is the screenshot diff that an operating system gets.

03

Architecture

mostly
State The frame, determinism and the licence boundary are enforced by lints in cargo xtask verify today. Capabilities exist and are tested by eight negative boots; the ring-based form of their operations does not exist yet and is scheduled for M5.

Three positions do most of the architectural work, and each is enforced mechanically rather than by review, because a policy that depends on somebody remembering it is a policy with an expiry date.

The frame, not a microkernel and not a monolith

Everything runs in one address space, for monolithic speed, and the safety boundary is drawn by the language rather than by the memory management unit. A small privileged frame is the only code permitted unsafe; services above it are unprivileged by construction because they cannot express the operations that would make them privileged.

The microkernel shape was rejected, and not on isolation grounds — it is stronger there. It was rejected because the hot path in this design is meant to contain no boundary crossing at all, which makes fast inter-process communication a solution to a problem the architecture is trying to delete rather than optimise. Asterinas is the existence proof that the framekernel shape reaches Linux-comparable performance with the unsafe trusted base held to a small fraction of the codebase. RFC 0001.

The consequence is that isolation reasoning becomes a property of the type system, so it has to be enforced by a machine or it is not enforced at all. Hence unsafe_code = "forbid" at the workspace root, exactly three crates overriding it, and cargo xtask lint-unsafe failing the build on a fourth. Every unsafe block in those three carries a // SAFETY: comment discharging the obligations that the corresponding # Safety section states — not a comment saying it is fine.

Determinism, as a substrate rather than a test mode

Nothing in the system observes nondeterminism except through an injectable Env. Time is not an instruction; it is a capability. Randomness is a capability. Interrupt arrival, ring consumer ordering, core assignment and allocation addresses are decided by a policy that is real in production and seeded under test — the same policy, not a test double.

env/src/lib.rs — the only legitimate source of time, randomness and ordering
pub trait Env {
    /// Current time. Virtual under simulation, hardware-derived in production.
    fn now(&self) -> Instant;

    /// Next pseudo-random value. Seeded under simulation.
    fn next_u64(&mut self) -> u64;

    /// The ordering policy.
    fn scheduler(&mut self) -> &mut dyn Scheduler;

    /// Civil time, if this machine has any business claiming to know it.
    /// None is the honest answer on a machine with no trustworthy clock:
    /// a fabricated timestamp is worse than a missing one precisely
    /// because it is usable. The default is None.
    fn wall(&self) -> Option<WallTime> { None }
}

The contract is that (seed, commit_hash) reproduces a run byte for byte. Deterministic simulation is the strongest known technique in systems reliability — FoundationDB and TigerBeetle are the standard citations — and it is almost never applied to operating systems, because kernels leak nondeterminism at thousands of unmarked places.

F's architecture removes nearly all of those places, and it did not do so deliberately. One ring interface gives a single interception point. No ambient authority means no hidden channels. User-space drivers make a modelled device a component substitution rather than a mock. Content-addressed state makes whole-system comparison a hash comparison. Every one of those decisions was made for speed or safety, and each hands simulation one of its preconditions for free. RFC 0004.

In practice this shows up as a list of things you may not write:

  • No Instant::now, no rdtsc, no thread_rng. Take an Env.
  • No HashMap or HashSet. Iteration order is seeded per process, so it is a nondeterminism source wearing a collection's clothes. Use BTreeMap and BTreeSet.
  • No f32 or f64. The two target architectures do not agree on them. Use an integer, or a fixed point with its scale in the name.
  • A new call site needs an allow-list entry with a reason in xtask/src/main.rs, which is a deliberately visible diff rather than a silent one.

cargo xtask lint-determinism is the check, and it is applied to xtask itself — the tool is subject to the policy it implements, which has caught the policy being wrong more than once.

Capabilities, with no root and no global namespace

A component holds exactly the authority it was handed and has no way to name anything it was not. There is no root capability that confers everything, and there is no global namespace to look things up in — the two mechanisms by which ambient authority normally re-enters a capability system.

Because a ring is named by a Channel capability, the capability table has to work before there is any ring to work it through. Four operations therefore exist temporarily behind the system-call door, and each one names the opcode that will replace it:

CallWhat it doesRetired by
CAP_INSPECTWhat a handle names.An opcode on the component's control ring.
CAP_DERIVEMint a weaker capability, or a copy.The same.
CAP_REVOKEWithdraw everything below a capability.The same.
CAP_MAPMap a frame into an address space.The same, with Sqe::cap as the frame handle.

That table is the shape of a rule worth understanding, because it recurs. RFC 0014 says a call may exist only if it cannot be an opcode on a ring. Read alone, that forbids all four of these, since every one of them could be an opcode and at M5 every one of them will be. RFC 0015 records the reading that resolves it: rule 1 governs permanent calls, and a second rule — every call added before the ring exists names the thing that replaces it — governs temporary ones. A call satisfying neither may not exist. cargo xtask lint-owed goes red on the day one of those reversal conditions is paid and the documents still describe the old shape.

The licence boundary is the isolation boundary

Imported driver source lives in third_party/, is differently licensed, and is reachable only over a ring. The permissive tree never imports it, and cargo xtask lint-licensing enforces that alongside the requirement that every file carries // SPDX-License-Identifier: Apache-2.0 OR MIT.

The two boundaries are deliberately the same boundary. This is the part that strengthens the safety claim rather than weakening it: code you did not write and cannot fully audit is placed where it can only be reached through an interface that already assumes its peer may be hostile, because that is the interface the ring had to be anyway. LICENSING.md and RFC 0003.

04

The ring

mostly
State The protocol, the cursor orderings, the suppression fence and the entry formats are built and are proved by bounded model checking over arbitrary peer bytes. The hardware fast paths — user-level interrupt delivery and shared virtual memory — are designed, argued and unbuilt.

Every service in F is a ring. That makes the ring the single most consequential piece of code in the system, and it has a harder job than io_uring does, because some of its peers are isolated components running imported driver code compiled from C, which may fault, hang or be compromised at any moment while holding a live channel.

Five requirements, in the order they constrain the design: no system call on the hot path; no copies, because buffers move by ownership; ABI stability across trust and language boundaries; a dead peer must not corrupt or hang us; and bounded latency rather than merely high throughput. The fourth eliminates more design options than the other four combined, and most importantly it forbids any lock in shared memory.

One channel is one mapping

Channel layout — one contiguous shared mapping
offset    size   contents
------    ----   --------
0x0000    64     ChannelHeader   magic, abi_version, ring_size,
                                 sqe_off, cqe_off, epoch, capabilities
0x0040    64     ProducerCursor  head: AtomicU32          // own cache line
0x0080    64     ConsumerCursor  tail: AtomicU32, flags   // own cache line
0x00C0    4*N    SQ index ring   u32 slots, N a power of two
...       64*N   SQE array       64-byte entries, one cache line each
...       32*M   CQ ring         32-byte completions, inline
...       var    inline arena    optional, for payloads under ~256 bytes

The indirection between the index ring and the entry array is worth keeping from io_uring: it lets a producer prepare entries out of order and publish a whole batch with one store. Ring sizes are powers of two so that index computation is cursor & mask rather than a division, and cursors free-run and are allowed to wrap — occupancy is head.wrapping_sub(tail), which stays correct across the wrap because unsigned arithmetic wraps the same way. There is never a separate count, because a count is a second piece of state that can disagree with the cursors.

The cursors get their own cache lines, and this is not a micro-optimisation. If head and tail share a line, every producer store invalidates the consumer's copy and every consumer store invalidates the producer's. If your first benchmark comes in several times slower than you expected, this is the reason, essentially every time — and it is the first entry in the diagnosis section of the corresponding claim, so a red result carries its own first debugging step.

The two orderings the whole thing rests on

Publishing an entry is a Release store; observing one is an Acquire load. That pair is the entire correctness argument for the data path: the Release guarantees the entry write is visible before the cursor advance that exposes it, and paired with the consumer's Acquire it is a complete happens-before edge.

Relaxed there passes on x86-64 and corrupts data on AArch64. On x86 both compile to a plain mov with only a compiler barrier; on AArch64 they become stlr and ldar. Total store order hides the entire class of bug the ring is exposed to, which is why testing the ring only on x86-64 is listed in CLAUDE.md as a mistake that has happened twice. Changing either ordering requires a litmus test that fails under the weaker ordering — not an argument that it is fine.

Notification suppression, and the fence that is not optional

Waking a peer costs three orders of magnitude more than a submission does, so the consumer publishes its intent instead of being woken blindly. While actively draining, it clears NEED_WAKEUP and producers skip the doorbell entirely; before sleeping it sets the flag and then re-checks the ring once more.

That second check is necessary and is not sufficient, and the RFC that says so was written because an earlier version of this text claimed it was. The two ends run Dekker's algorithm: the producer stores head then loads flags, the consumer stores flags then loads head. Store-load is the one reordering that total store order still permits, and Release/Acquire do not forbid it. Without a SeqCst fence on the producer side, both sides can see nothing and the consumer sleeps holding work. The re-check closes the case where the consumer's flag write is late; it does not close the case where the consumer's ring read is early. RFC 0020.

On a deadline-class core the consumer should never sleep at all. It parks with user-level monitor-and-wait — UMONITOR/UMWAIT on x86, WFE on ARM — armed on the cursor's own address, so the core drops to low power but wakes on the store itself. No interrupt, no scheduler, no jitter tail. This is one of the silicon capabilities the thesis is about, and it is the easiest of them to adopt: the instructions have shipped for years and are almost entirely unused.

The doorbell itself is abstracted behind one function with three implementations — user interrupt, kernel inter-processor interrupt, and pure polling — selected at channel creation from what the hardware actually reports rather than from what it was compiled for. Keeping all three and measuring the difference between them is one of the cleanest results this system can produce, because nobody has published it for a general-purpose IPC path.

Buffers are owned, not shared

A buffer belongs to exactly one side at a time, and the transfer of ownership is enforced by the compiler rather than by convention. A process registers a memory region once and receives a BufferSetId; the IOMMU mapping is established at that moment and never touched again, and individual operations then reference (buf_set, index, offset, len) — no per-operation pinning, no page-table work, and no validation beyond a bounds check against a size the frame already knows. RFC 0024, RFC 0028.

Registration exists to solve a problem newer silicon removes. With IOMMU shared virtual memory — process address space identifiers, address translation services, page request interfaces — a device walks the process's own page tables and takes ordinary page faults, so there is nothing to pin and nothing to register. The buffer triple becomes a plain virtual address and the PASID is carried by the channel rather than by the entry. The registration path stays, because the hardware is not universal; it becomes the fallback rather than the design.

Surviving a peer that is hostile or dead

Every field a peer can write is validated before it is used, and the validation is proved rather than reviewed: cargo xtask prove runs bounded model checking over the ring's validation paths for arbitrary peer bytes, and then requires each deliberately injected defect to fail the harness that states the property it breaks. cargo xtask hostile generates a very large number of hostile peer operations, and a hang is counted rather than waited on. RFC 0046, RFC 0048.

The header carries an epoch, which is how a channel survives a peer that died and was restarted: entries stamped with a previous epoch are not the new peer's, and the distinction is in the wire format rather than in a convention both sides have to remember.

What runs on it

05

Components

partly
State The manifest schema is enforced by cargo xtask lint-manifests with a fixture breaking each rule, and the tree contains components. The supervisor, the state tree and in-place transfer are specified in RFCs and are in progress rather than finished.

A component comes into existence in exactly one way, is controlled through exactly one path, holds exactly what it was handed, and ends in a way every other party can see. There is no fork and there are no signals. RFC 0008.

Both absences are deliberate and both are load-bearing. fork is incompatible with a capability system that has no ambient authority, because the whole point of fork is that the child inherits everything without anybody naming what. Signals are asynchronous control flow delivered into a process that did not ask for them, which is the opposite of a system where everything arrives on a ring the process holds a capability to.

The manifest is what a component is before it runs

One file per component, called manifest.toml, in the permissive tree. It declares the image, the speculation domain, the capabilities routed to it and the ones it may ask for, the protocols it speaks and on how many rings, what its supervisor does when it ends, and what admission may refuse it. user/virtio-blk/manifest.toml is the worked example; docs/manifest.md is the schema as prose and xtask/src/manifest.rs is the schema as code.

SectionWhat it declaresWhy it cannot be decided at run time
top levelImage, schema version, speculation domain.RFC 0005: a domain kind is declared and never inferred.
[[capability]]What is routed in, and what may be asked for.A component holds what the manifest declared and the supervisor supplied. Nothing else is nameable.
[[ring]]Protocols spoken, and on how many rings.A ring is a capability; it cannot be conjured by a process that was not given one.
[restart]What the supervisor does when the component ends.The policy has to exist before the failure does.
[reservation]What admission may refuse.Admission is arithmetic and refuses; arithmetic needs a declared demand.
[transfer]What the component declares about being updated in place.RFC 0063: quiescence is asserted by the occupant, and declared in advance.
[[device]]The part of a device a driver binds.RFC 0067: the topology never inherits a scan order.
[[state]]What the component publishes about itself.RFC 0065: a spawn refuses a component that does not declare its tree.
The schema is closed, because it is a parser's input. A field the reader does not know is refused, not skipped. A value outside a table is refused, not mapped to the nearest one. A field that means nothing under the declared policy is refused, not ignored. The cost is that every schema change is a version bump and a visible diff; the benefit is that no two readers can hold different beliefs about one file, which is exactly how a format acquires two incompatible interpretations and no error message.

The manifest is valid TOML, so any TOML reader accepts it — but the lint accepts strictly less than TOML does: comments, [table] and [[array]] headers, and key = value. Where docs/manifest.md and the lint disagree, the lint is wrong and the document is what it is wrong against; the fix is to change the lint and add the fixture that would have caught it.

A spawn is where the declarations are checked

A component is spawned from a manifest named by content hash. That single sentence carries three consequences worth separating. The hash is what measured boot extends into, so the identity of what is running is the identity of what was declared. The manifest is the topology's unit, so the set of components is a compiled artefact rather than a runtime discovery. And a spawn checks every declaration, so a component that under-declares fails at spawn rather than at the first moment it needs the thing it did not ask for.

cargo xtask lint-components closes the other half: the components this tree declares must be the components it builds. A manifest with nothing building it is a component no downstream count will ever look for, which is a quieter failure than a missing file.

Supervisors, places, and ending

A supervisor is itself a component, and the frame answers its ring like anybody else's (RFC 0073). It is told when it is started (RFC 0076). The thing it supervises occupies a place, and a place survives its occupant (RFC 0041) — which is what makes restart and in-place replacement the same mechanism seen from two angles, rather than two mechanisms that have to be kept agreeing.

Ending is visible to every party with an interest, rather than being a condition each one discovers by timing out. cargo xtask chaos kills every component under sustained load at seeded moments and requires that no client observes anything except added latency; cargo xtask swap replaces every component by the route its own manifest declares and requires that no client observes a dropped operation, comparing the state that crossed against what the outgoing instance held.

06

Resources

ahead
State Ahead of the code. The admission arithmetic and the ADMISSION error domain exist and are proved; the five subsystems below are the argument in docs/design/deadline-all-the-way-down.html and are largely unbuilt. Read this chapter as the shape the work will take, not as a description of behaviour you can observe.

Mainstream systems have roughly five resource policies — a CPU scheduler, a page reclaimer, an I/O scheduler, a network queue discipline, a GPU arbiter — and they do not know about each other. A request that needs all five gets five independent answers and no guarantee, which is why tail latency in a conventional system is emergent rather than designed.

F's position is that there is one discipline and five places it is applied. The discipline is the deadline: it is declared by the requester, it inherits downward through every ring the request crosses, and it decays as the request proceeds so that a stale deadline cannot outrank a fresh one forever. RFC 0025.

Admission is the load-bearing part

The part that makes a deadline mean anything is not the scheduler; it is the refusal. Admission is arithmetic over declared demand, and it refuses — it does not degrade, queue, or best-effort. A reservation that cannot be satisfied is denied in the ADMISSION error domain, and the component finds out at the moment it asks rather than at the moment it misses.

This is why the manifest carries a [reservation] section. Arithmetic needs a declared demand, and a demand that is discovered from behaviour is a demand that can only be measured after the guarantee has already been broken. RFC 0007 and RFC 0050. abi/proofs proves the arithmetic under bounded model checking, because a refusal that is wrong in the permissive direction is a guarantee that silently is not one.

cargo xtask admission is the boot that exercises it, and its shape is the shape of every serious check in this project: refuse an over-subscribed reservation, put a granted one under adversarial load, and run two controls beside it — the same load with no reservation, which must miss, and an over-subscription, which must be refused and run nothing. A guarantee with no control beside it is a guarantee that was never tested against the possibility that the load was simply easy.

The five places it is applied

  • CPU time. Four classes rather than a priority number. Heterogeneous cores are the reason placement is decided by slack rather than by a fixed affinity: a big core and a little core are not two speeds of the same thing. User-level runtimes sit above this and inherit the deadline rather than inventing a second scheduler.
  • Memory. Three resources, not one — capacity, bandwidth and tier. Tiering is measured rather than guessed, which is the whole difference between a memory tier and a cache.
  • Storage. A content-addressed object store over a zoned mapping. The crates are hash (the one SHA-256 in the tree), blob (the chunker and the store), zone (the zoned mapping and the collector) and index. The collector is three invariants and a batch-class consumer rather than a background thread with a heuristic. RFC 0059.
  • Network. What is written and what is not, with authority and contention decided by the same declarations everything else uses.
  • Accelerators. Reached as peers on a ring, not as files.

The storage layer is the one with the most code behind it today, and it is worth understanding as a single idea: content addressing makes whole-system state comparison a hash comparison, which is what makes deterministic simulation able to say two runs diverged, and here is the subtree they diverged in rather than two runs diverged. cargo xtask compare is that capability exposed directly. It is also why a generation swap can be an update and an attestation at the same time: the root hash of the generation tree is what the machine is running. RFC 0012.

Every immature bet in this chapter has a fallback, and the fallbacks are part of the design rather than a contingency. Zoned storage, memory tiering, user interrupts and shared virtual memory are all silicon capabilities that are unevenly available. The rule is that each is abstracted behind one interface with a conventional implementation beside the new one, chosen from what the hardware reports. A design that only works on the best available machine is a demonstration, not an operating system.
07

The interface

ahead
State Ahead of the code, and further ahead than any other chapter. Four decisions are recorded as RFCs 0077 through 0081 and a fifth as RFC 0083; the interface/ crate exists. There is no compositor. Epoch E3 is the longest and hardest in the plan and has not opened.

The display in a conventional system receives pixels. Every layer above it — the application, the toolkit, the compositor — converges on a rectangle of colour, and everything the system knew about what was being shown is discarded at the last step. The consequences are familiar enough to be invisible: accessibility has to reconstruct meaning by inference, automation drives the system by pretending to be a mouse, and a screen reader and a test harness solve the same problem twice and badly.

F's position is that the application sends structure, and the pixels are produced at the end by one component that owns the whole machine's scene.

Deltas, not frames

The compositor holds a scene graph and receives deltas to it, not rendered output. A frame nobody asked for is not drawn (RFC 0023), which turns an idle interface into an idle machine rather than into a machine re-rendering an unchanged image sixty times a second. Synchronisation is explicit only — there is no implicit fence anywhere in the pipeline, because an implicit fence is a latency cost nobody can find.

The semantic layer, and the closed vocabulary

Above the scene graph sits a semantic model: a structure that says what the interface is rather than what it looks like. Projection turns that one structure into many presentations — a screen, a screen reader, a test harness, a remote session, a command line — and the payoff is that those stop being separate implementations that drift.

The vocabulary of node kinds is closed (RFC 0077). This is the decision most likely to be argued with, so the reasoning is worth stating plainly: an open vocabulary is one where any application can introduce a node kind nothing else understands, and a projection that meets an unknown node has no honest option. Closing it means the vocabulary has to be right, and that the version is negotiated between peers with an unknown role not being representable on the wire at all (RFC 0083) rather than being a value everybody agrees to ignore.

A canvas declares its content, or it is an escape. RFC 0078. A self-rendering surface — a video, a map, a game — is unavoidable, and the temptation is to let it be opaque. An opaque canvas is a hole in every projection at once, so a canvas must still declare what it contains. The rate at which applications escape into canvases is a registered claim, because it is the number that says whether the semantic layer is working or is being routed around.

Two rules about failing

The interface has two decisions about degradation, and both were made before the thing that would need them was built, which is the opposite of how this usually goes.

  • A theme may not make an interface unreadable (RFC 0079). Theming is customisation, and customisation that can produce an unusable result is a defect with a preferences dialog in front of it. A hostile theme is refused.
  • The fallback ladder is decided before it is needed (RFC 0080), and at the bottom of it the frame draws the log when nothing else can (RFC 0081). A system whose failure mode is a blank screen is a system that cannot tell you why it failed. This is the rung that makes every rung above it debuggable.

What would falsify the whole pillar is stated in docs/design/ring-scene-boot.html part III and is worth reading before you accept the argument: if the indirection costs the latency budget, or the vocabulary turns out to be the wrong size, the position does not survive.

Part III

Underneath, and around

08

Under the hood

mostly
State Built and tested. Per-CPU state, the system-call door, multi-core bring-up and the shootdown handshake all run; cargo xtask cores exercises four core configurations and cargo xtask lint-percpu enforces the rule below on every commit.

Kernel state is per-CPU, and nothing locks

Every mutable static under kernel/ is a PerCpu<T>. There is no lock anywhere in the kernel, and that is not a performance choice — it is what makes the frame's behaviour a function of its inputs rather than of its timing, which is what determinism requires of the one component that cannot be simulated away.

The rule has exactly one exception, and the exception is precisely bounded rather than being a general permission:

A shard is one core's, except for a word two cores handshake through, and a handshake word is an atomic on both sides. Four PerCpu<u64> shards in kernel/src/smp.rs are reached by a core that does not own them — a mailbox, and a page, a sequence number and an acknowledgement for the translation-buffer shootdown. Every one is a machine word, sits in the slot of the core it is about, and every access on both sides is an atomic with its ordering named at the access. A fifth needs an argument. RFC 0016.

That exception exists because bringing up a second core needs two things a single-core kernel does not: a core has to be told to do something, and it has to say when it is done. That is a handshake, and a handshake cannot be per-core state by definition. The RFC exists to record exactly how far the rule was bent, so that the next bend is a visible decision rather than a precedent.

The system-call door

The syscall entry exists so a process can reach the frame when there is no ring to reach it through. It is not an interface and it does not accumulate one. Three rules govern it: a call may exist only if it cannot be an opcode on a ring; every call added before the ring exists names the thing that replaces it; and nothing behind the door is measured, tuned or made fast.

That third rule is the one that surprises people, so here is the reasoning. The entire architectural claim of this system is that the hot path does not cross this boundary. Work spent making the crossing cheaper is work arguing against the claim — it makes the door more attractive, which makes it more used, which makes the claim less true. RFC 0014.

The permanent calls at M3 are ANNOUNCE (the process says it exists, which becomes the channel-setup handshake at M5), PROGRESS (asks the frame how much of its time the process has taken, and is what a blocking wait on a ring replaces) and EXIT. A call the frame does not have is refused as an argument error, not an authority one: the process was permitted to ask.

Faults, and a core that does not answer

A fault class states its response (RFC 0039) rather than being handled wherever it lands. cargo xtask fault boots deliberately into each of six — page fault, undefined instruction, double fault, no-execute, write-execute and stack — and requires the response the class declared.

A core that does not answer is held, and not fatal (RFC 0068). A machine that reports eight logical processors and answers with two must still reach M0, holding the six that are not there and saying how far each one got. This is the sort of behaviour that is easy to get wrong in a way nobody notices until the hardware is unusual, which is why it is four separate boots in cargo xtask cores rather than a unit test.

Boot, and what it extends

Boot compiles a generation: user/generation.toml becomes a record tree, folded to one root hash, packed with the component files into one boot module named by that root. Source that is not in canonical form is refused with the canonical form printed as a diff, never silently reordered — the same closed-input discipline the manifest uses, for the same reason.

The root hash is the attestation. cargo xtask attest is five boots asking, in order: what is this machine running; is the answer the same twice; does a modification to the frame move it; does the frame refuse to publish a root it cannot measure its way to; and is the reserved zero reachable. There is no signature and no freshness, and RFC 0012 says plainly what that does and does not prove.

How work reaches this repository

runs
State This is how the repository works today. Where something is aspiration rather than practice, the sentence says so.

Six stages, each naming its artifact and who is allowed to close it. docs/sdlc.md is the full route; this is the shape.

intent → spec → plan → diff → review → claim
1 plan      intent/NNNN-name/intent.md      a person wants something
2 design    intent/NNNN-name/spec.md        we agree what it means
3 build     plan.md, then a diff            it gets made
4 test      cargo xtask verify              it checks its own work
5 deploy    REVIEW.md, then a tag           it leaves
6 maintain  ops/bands.yaml, evals/          it tells us what happened

The three files in an intent directory are separate because they are written by different people at different times and they fail differently. An intent.md that is wrong wastes a conversation. A spec.md that is wrong wastes a week. A plan.md that is wrong wastes an afternoon. Collapsing them hides which one was wrong.

intent.md is never edited to match what was built — that belongs in the spec or an RFC. It records what somebody wanted at a moment, and rewriting it destroys the only evidence of whether this project builds what people ask for. It is also the only one of the three a non-engineer writes, so it should stay writable by somebody who has never run cargo; do not ask it for file paths.

Four identifier spaces, and what links to what

This repository is authoritative. There is no ticket system to reconcile with, and four numbered spaces point at each other: intent/NNNN is what somebody wanted; TODO.md task ids like E2-B04 are permanent and ranked by what they unblock; docs/rfc/NNNN are decisions and reversals; claims/NNNN are numbers with baselines and thresholds.

An intent that produces a decision gets an RFC. One that produces a number gets a claim. One that produces neither produced a patch, which is fine and needs no ceremony. Numbering is permanent in every space: an abandoned intent stays in place marked withdrawn with one line saying what was learned.

What an RFC owes

An RFC is required whenever a change contradicts something already written down, reverses an earlier decision, or widens a policy allow-list. Copy docs/rfc/0000-template.md. The section that matters, and the one reviewers actually read, is What would reverse this — a decision recorded without the conditions that would undo it is an opinion with a number on it.

cargo xtask lint-owed is the mechanism that keeps that section honest. It declares the reversal conditions this tree has named and not yet paid, and it goes red on the day one of them is paid and the documents still describe the old shape. A reversal condition nobody checks is a reversal condition that quietly expires.

What a claim owes

Any number that reaches a published document needs an entry in claims/ carrying a statement, a baseline that is a configuration rather than a description of one, a workload, the metrics, thresholds, the class of machine required, a one-command reproduction, and a diagnosis section so that a red result arrives with its own first debugging step.

Expect a reproduction to refuse to record, and understand that the refusal is the feature. A timing measurement is only recorded on a machine that can defend it — bare metal, the reservation components obtained by partition, thermally stable. Anywhere else the workload still runs and the distribution is still printed, and recording is refused with the reason. A number with no environment attached is how a benchmark becomes marketing, so the default is to refuse. claims/runner-class-A.md is the specification of a machine that may record, and at the time of writing it is a name rather than a machine.

Two lints keep the registry and the documents agreeing. lint-claims fails if any document cites a value the claim no longer has — a number in a document is never allowed to be a second copy of a claim. lint-claim-owners requires every claim to name the document that owns it, because a claim nobody owns is a claim nobody can be asked about.

Review, and what an agent may not close

Review runs four passes in a fixed order — policy, bugs, security, compliance — with a severity ladder and a cap on nits. It runs on every pull request. It may push fixes; it may not approve and it may not merge, and branch protection enforces that in the repository settings rather than in a file, because a rule that lives only in a document the agent reads is a rule the agent can be talked out of.

The release gate works the same way: a hook blocks publishes, tag pushes and image pushes unless an environment variable names an authorisation, and an agent cannot set that variable for itself. A gate the gated party can open is a log entry.

Working in parallel, and the mistake that keeps happening

Independent tasks run in separate worktrees, and the build volumes are per-checkout so two sessions do not fight over target/. That much is easy.

Four green worktrees do not compose. Twice now, separate trees each took one registry entry twice — an RFC number, a reserved byte — and once two of them split one grammar between a reader and a composer. Every tree passed and the merge could not boot. Run the merged tree: the merge is the first execution of a program nobody has run. docs/postmortem/0001 is the write-up, and the practical consequence is that before you take a number in any of the four identifier spaces, you check the other branches and not just main.

The rest of the recurring mistakes are in CLAUDE.md under Common mistakes, which is a scar list rather than a style guide — a line is added when the same mistake has happened twice, and removed when it becomes a hook instead of advice.

The error space

Errors are structured rather than numbered: a domain says what kind of thing went wrong, and a code within the domain says which. The domains are closed, and a service may add a code to a domain without any peer having to learn it in advance. RFC 0010.

DomainMeaningWhat the caller should conclude
AUTHORITYYou do not hold what you would need.Not retryable. Ask whoever routed your capabilities.
ADMISSIONThe demand was refused as arithmetic.Not retryable unchanged. Declare less, or wait for a different machine.
RESOURCESomething is exhausted right now.Retryable in principle.
PEERThe other side of the ring.Depends on the code; a dead peer and a slow one are different.
ARGUMENTYou were permitted to ask, and asked wrongly.A bug in the caller.
DEVICEThe hardware.Depends on the code.

The distinction between AUTHORITY and ARGUMENT is the one worth internalising: asking for something you have no right to name is an authority failure, and asking wrongly for something you may ask for is an argument failure. A frame that conflates them leaks the existence of things the caller is not supposed to be able to name.
