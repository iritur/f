What in this book runs

This is the book with the least distance between it and the tree, because the apparatus was built before most of the system it measures. That is deliberate — docs/design/proving-ground.html argues that an evidence apparatus retrofitted onto a mature kernel is an apparatus that will never be built — and it means nearly every command in this book executes today.

It also means this is the book where the gaps carry the most information, so chapter 12 is not an appendix. Read it.

Part I

What a green result is worth

01

Why this book exists

true
State An argument about method. Nothing in this chapter can be ahead of the code because it describes how the project reasons rather than what it does.

An operating system that claims a large constant factor over the incumbent is making a claim that is very easy to make and very hard to be held to. The usual failure is not dishonesty. It is that the benchmark was run on a machine nobody else has, against a baseline nobody tuned, reporting a mean that hides the stalls the architecture exists to eliminate, with no way for a stranger to re-derive any of it. Every step of that is defensible in isolation and the result is marketing.

So this project decided early that the apparatus deciding whether its claims are true would be built before most of the claims, and would be allowed to refuse. That is unusual enough to need its own book.

The rule this whole book is organised around

A check that has never failed is a check nobody has tested. Every instrument in this book has a mode that deliberately breaks the thing it watches and requires the instrument to notice. A test suite that only ever goes green is measuring whether it runs, not whether it works — and the difference between those two is invisible right up until the moment it matters.

That rule is not a slogan here; it is four separate commands, and running them is part of the ordinary local loop:

CommandWhat it breaksWhat must then happen
cargo xtask mutateBuilds the kernel with a deliberate defect.The boot must go red, with a panic in the log. Then the same boot without it must go green.
cargo xtask sweep --mutateArms a deliberate defect in the simulator.The sweep and the corpus must both find it, then both go quiet when it is disarmed.
cargo xtask proveInjects defects into the proved code.Each must fail the harness stating the property it breaks — and no other.
cargo xtask generation --mutateCompiles the build path into the frame.The comparison must go red and name the frame.

cargo xtask lint-mutations then closes the obvious hole: it refuses any manifest that turns a deliberate defect on by default. A defect that ships is not a test.

The second rule: a guarantee needs a control

Almost every serious check in this tree runs the thing twice and requires the two runs to disagree. cargo xtask user is the clearest example: seven boots in which a process at ring 3 violates one isolation rule each, six of which must fault — and a seventh which must not. That seventh boot is what stops the other six passing for the wrong reason, because a kernel that faults on everything passes a suite of six fault tests perfectly.

cargo xtask admission has the same shape: a granted reservation under adversarial load, beside the same load with no reservation, which must miss. A guarantee with no control beside it has never been tested against the possibility that the load was simply easy.

What you should be most suspicious of

Nearly every result in this project is an assertion about an emulator. The kernel has run outside QEMU three times, all on virtual machines, and has never booted on bare metal. Nothing about this is failing — the tests pass, the boots are green — and that is exactly what makes it easy to miss. Chapter 12 is the full account. If you read one chapter of this book adversarially, read that one; if you read two, read that one and chapter 06.

The reason that sentence is in the first chapter rather than buried at the end is a position this project takes about documentation generally: a gap that is stated is a gap somebody can act on, and a gap that is implied by an absence is one that gets rediscovered expensively. docs/TESTING-STATUS.md exists for exactly this, and it is the file this book is checked against.

02

The seven layers, and where each stands

runs
State The layer definitions are from docs/design/proving-ground.html. The status column is read from docs/TESTING-STATUS.md, which is maintained against the tree; where the two disagree, that file is right.

Seven layers, each answering a question the others cannot. The point of the decomposition is not tidiness — it is that each layer has a different failure mode, and a project that runs only one kind of check has a blind spot shaped exactly like the checks it does not run.

LayerThe question it answersStatus
L0  Determinism substrateCan a run be reproduced at all?built
L1  Deterministic simulationWhat happens to the components under seeded faults?built above the frame
L2  Concurrency & memory modelWhat does the memory model permit?stress only
L3  ProofDoes a counterexample exist inside a stated bound?built, narrow
L4  FuzzingWhat does a hostile peer do to the one surface?built
L5  Performance regressionDid this commit make it slower?harness only
L6  Hardware in the loopWhat does a photodiode see?absent
L7  Claims registryWhich numbers may this project say out loud?built, gating

Two of those statuses are worth reading rather than skimming. L5 is a harness with no change-point detection, because change-point detection needs commit history to reason about and that is a later phase; the harness records distributions and marks the counters it cannot read as absent, which is the honest half. L6 is absent and correctly so — a photodiode rig measures input-to-photon latency and there is no compositor yet to put photons on a screen.

The layer with no row

A taxonomy built around simulation, proof and fuzzing has no natural home for run the real thing and try to break it. That is chapter 09, and it is where most of this project's evidence currently comes from.

The absence of a row is stated rather than papered over, and that is the pattern to learn from this book. It would have been easy to file the fault boots under L1 and the capability boots under L4 and have a tidy seven-row table with nothing missing. The table would then have described a taxonomy rather than a tree. A category that does not fit is information about the category.

The two cadences

Not everything runs on every commit, and which instrument runs when is itself a decision. cargo xtask verify is the local loop — lint, test, boot, mutate — and is what a session runs before a human is asked to look. The expensive instruments run on a schedule: the proofs take long enough that putting them in verify would mean nobody ran verify, and a nightly sweep varies its base seed so that successive nights cover new seed space rather than re-covering the same.

docs/test-taxonomy.md is the full matrix — every property, the layer that covers it, the cadence it runs at, and who owns each gap. It is long, and it is the document to read if you want to know whether a specific property is checked rather than whether the apparatus exists.

Part II

The instruments

03

Determinism, and the instrument that tests it

runs
State Built. The lint runs on every commit, and the contract check runs at every boot against both the seeded and the hardware environment on the same run.

Everything else in this book depends on this layer, which is why it was built first and why it is the one property the project treats as unretrofittable. The contract is that (seed, commit) reproduces a run byte for byte. F Foundations chapter 03 describes the mechanism; this chapter is about how you would know it is true.

The instrument

Checking the substrate, rather than trusting it
cargo xtask trace          # two runs of this commit must produce one trace hash,
                           # and one unseeded read of time must break that
cargo xtask trace --hash   # print this run's trace hash and nothing else

cargo xtask sim --hash <scenario> <seed>
                           # the same question, one scenario at a time
cargo xtask compare        # two whole-system states as two hashes,
                           # and the subtree they differ in

Note the second half of the trace line, because it is the whole design in one clause. It is not enough that two runs agree; an unseeded read of the clock must make them disagree. A determinism check that only asserts agreement passes trivially on a program that does nothing, and passes just as well on a program whose nondeterminism happens not to have been exercised on the day you ran it.

The same trap, one level down, stated in the sweep code: a run with nothing in it produces a short trace and a perfectly stable digest, which is the one result a check must never report as a pass. That sentence is why --seeds, --scenarios, --clients, --window, --ops and --jobs all refuse zero, and why a report whose grid held no trials is an error rather than a clean sweep. RFC 0042.

Enforcement, and why it is a lint rather than a review item

cargo xtask lint-determinism refuses any direct source of nondeterminism outside an allow-list, where each allow-list entry carries a reason. The list of forbidden things is in F Foundations; what matters here is the mechanism. A new call site is a visible diff to xtask/src/main.rs rather than a line of code nobody notices, and the lint is applied to xtask itself — the tool is subject to the policy it implements, which has caught the policy being wrong more than once.

The boot does the other half. kernel/src/env.rs and kernel/src/main.rs run env/src/contract.rs against the seeded environment and the hardware-derived one on the same run, so a divergence between the two is caught by the system rather than inferred from a failing test somewhere else.

One derivation, and streams that split

A subtlety worth knowing before you read the simulator chapter. Everything drawn from a seed comes from one derivation — env/src/split.rs — and separate call sites get separate streams derived from it by identity rather than by consuming a shared generator. A wall-clock reading is a different stream under the same seed than a random draw, so stamping a timestamp and drawing a value cannot correlate and neither moves the other. RFC 0026.

That sounds like a detail and is load-bearing: without it, adding a draw anywhere changes every subsequent value everywhere, and a seed stops reproducing a run the moment anybody adds a line of code. The property the whole apparatus rests on would have decayed silently.

04

The simulator, and its declared scope

runs
State Built, above the frame. Virtual time, seeded ordering, device models on the real ring types, component substitution, snapshot and restore, and a scenario set that must each reproduce from its seed.

Deterministic simulation is the strongest known technique in systems reliability and is almost never applied to operating systems, because kernels leak nondeterminism at thousands of unmarked places. F's architecture happens to remove nearly all of them — one ring interface is a single interception point, no ambient authority means no hidden channels, user-space drivers make a modelled device a substitution rather than a mock. Those decisions were made for speed and safety, and they hand simulation its preconditions for free.

What it does not simulate, said in advance

The simulator runs the components, not the frame's instructions. It will never catch a bug inside the frame's own algorithms. This is RFC 0032 — a decision recorded before the simulator was built, rather than a limitation discovered when somebody asked why a kernel bug got through. The frame is covered instead by the boot suite, the mutation harness and the proofs, which is chapters 07 and 09.

Scope declared in advance is worth more than scope discovered later for a reason specific to this kind of tool: a simulator that is believed to cover the frame is worse than no simulator, because the belief displaces the checks that would have covered it.

A modelled device is a peer, not a mock

The device models for block, network and graphics speak the real ring types — the same abi/ structures a physical driver uses, not a parallel test interface. RFC 0034. A mock is a second implementation of an interface, which means it is a second thing that can disagree with the interface and be wrong in a way the test cannot see. A peer on the real types cannot drift, because there is nothing for it to drift from.

The same logic drives component substitution: swapping a real component for a modelled one is a change to which image a manifest names, not a change to how anything is wired.

Both halves of reproducibility

Every scenario must reproduce from its seed and must move when the seed moves. cargo xtask sim runs every scenario twice at one seed and once at another: the pair must agree and the odd one must not. A scenario that produces the same trace for every seed is a scenario that is not exercising anything, and it would otherwise sit in the suite forever looking like coverage.

Faults that assert rather than print

Seven fault classes, each asserting a response rather than printing one, per RFC 0039 — a fault class states what should happen and the test requires it. This is the layer whose hook was deliberately built before it was needed: once code asks its Env whether an operation should fail, adding a fault class is a change to one file, whereas code that assumes success has to have every call site revisited later.

Joining the two halves

The simulator and the real boot are two accounts of the same system, and two accounts that are never compared will eventually be about different things. cargo xtask sim --join boots the real kernel, reads the component hashes out of its log, and requires the set the simulator runs to be the set the boot spawned — joined at an artefact rather than at a sentence. RFC 0035.

And RFC 0036 is the other half of that: the join names the gap it cannot close. JOIN_GAP is a declared constant that a lint compares against the tree, so it goes red both when the gap grows and when the reason for it stops being true. That is the difference between a known limitation and a forgotten one.

05

Sweeps, and an oracle that names no bug

runs
State Built, with a committed corpus, automatic minimisation, sharding, and a mutation mode that requires the sweep to find a defect it was not told about.

A scenario suite checks the things somebody thought of. A seed sweep is the instrument for the other category, and it is the one you can point at your own checkout to go looking for something nobody has found yet.

One command, from the repository root, Docker the only prerequisite
docker compose -f docker/compose.yaml run --rm dev cargo xtask sweep

cargo xtask sweep --help      # what a seed is, what a finding is, what to do with one
cargo xtask sweep --mutate    # arm a defect; the sweep AND the corpus must find it
cargo xtask sweep --corpus    # replay every trial that ever found something
cargo xtask sweep --base <s>  # the seed the sweep derives from; a nightly varies it

The oracle must not know what it is looking for

A seed sweep is checked by properties that name no scenario, no fault class and no defect. RFC 0040. The five properties in sim/src/check.rs are expressed over the trace's own vocabulary and were written before the deliberate defect that tests them existed. The reasoning is exact: a sweep's premise is that the bug is not known in advance, so an injected bug that had to be named by an assertion written for it would have been found by the assertion rather than by the sweep — and the sweep would have been credited with a capability it does not have.

This is also why the oracle is deliberately separate from the fault classes of chapter 04. Those assert a stated response and are right to; that shape is correct for a class and wrong for a sweep.

A finding is a command line, not a symptom

Every failure is minimised and printed as a line that judges itself: it is spelled --check, which exits non-zero and names the property that broke, rather than --trace, which prints a wall of output and exits zero. cargo xtask sweep --mutate takes that line off the report and runs it, requiring non-zero armed and zero disarmed — so what is asserted is the command, not the shape of a string that looks like one.

Two details in the minimiser are worth knowing because they are the kind of thing that is wrong in most minimisers:

  • A finding's signature is the first check that fails, and minimisation preserves the signature rather than merely preserving a failure. Neither knob of an injection is a subset operation, so a minimiser that accepted any failure will happily conclude that earlier strikes were not required and hand you a reproduction of a different bug.
  • The sweep decides what is smallest and says in what terms. Size is a lexicographic tuple — armed classes, strikes actually made, operations, clients, window, how late injection begins — and the report leads with the smallest reproduction across the whole sweep. That is no human triage made mechanical: read finding one.

If you find something, add the argument list to sim/corpus.txt so it stays found. That file is append-only, a corpus line is an argv, and --corpus replays all of it and requires each line to be clean now. It is the permanent regression half of a sweep, and it ships in the release package.

What a sweep costs, and what it cannot catch

RFC 0042 is the amendment that made those two things stated quantities rather than assumptions, and it exists because the earlier shape could report a green result for a run that had not happened.

  • The leak is a budget rather than a hope. Every trial leaks its clients' buffer regions, because a component's region is granted for the life of the component and a simulated component's life is the run. That was bounded when a run was a process and is bounded by nothing once a sweep runs many trials in one. So a grid past the budget is refused before a trial runs, with the largest acceptable value printed beside the refusal, and cargo xtask sweep shards on that ceiling — where a shard is a range of the same seed derivation, so the shards together try exactly what one process would have tried, in the same order.
  • Zero is refused everywhere it means nothing ran, per chapter 03.
  • The report prints its own wall clock and says in the same breath that the number is in no verdict in it. A container is the one environment the benchmark harness refuses to record a timing in, so the cost of a sweep is reported as a courtesy and is not evidence.

A finding carries the commit as a git switch in front of it — but only when the sweep ran in a tree that was exactly that commit. On a checkout you have edited it does not, because checking the commit out would throw away the changes that found the thing. The report's tree line says which of the two you are reading. A sweep of your own work in progress is a perfectly good way to find a bug; it is not a bug report anybody else can run until you have committed.

06

Concurrency, and the test that did not catch it

partly
State Stress tests run, on both architectures, and have a known and measured blind spot. Model checking is open and has been for several epochs. This is the weakest layer in the book and the chapter is written accordingly.

The ring rests on one Release store and one Acquire load. Getting that pair wrong produces a defect that passes every test on x86-64 and corrupts data on AArch64, because total store order hides the entire class of bug the ring is exposed to. So the litmus tests run on both architectures, and the AArch64 job is where they mean anything.

What happened when that was checked

Two deliberate defects weaken the publishing stores from Release to Relaxed. CI required the litmus suite to fail with them armed, on the AArch64 runner — the machine where that weakening is a real defect. The suite passed. Both steps were then removed as gates, because a gate asserting that a probabilistic test catches a specific reordering goes red on a Tuesday for reasons nobody can reproduce.

Read that carefully, because it is the single most useful paragraph in this book. The standing position is not the soft version — stress tests are empirical, so there is a theoretical gap. It is the sharp version: the suite has been shown not to catch the exact defect it was written to guard against, on the exact hardware that defect is about.

That is what the apparatus is for. The mutation harness of chapter 01 was pointed at the concurrency suite, the suite failed to notice, and the result was written down and the misleading gate removed — rather than the gate being kept because it was green. A project without that harness would still have a passing litmus job and would believe it meant something.

What would actually close it

Model checking explores what the memory model permits; stress tests explore what one machine happened to do on one afternoon. Those are different questions and only the first can settle the ordering. RustMC is the open task, and it has been open long enough that its absence is a standing fact about this project rather than a temporary state.

And it will arrive with a caveat, stated here in advance rather than discovered next to a result. A checker brings its own toolchain (RFC 0022), so it checks the protocol as written and not the machine code this tree ships. Atomic orderings are specified by the language rather than chosen by the backend, which makes that a small gap — but it is a gap, and a citation of a model-check result owes the reader this sentence.

What does cover some of it

The proofs of chapter 07 cover the ring's validation paths against arbitrary peer bytes. That is a different question from what the memory model permits, and it is worth being precise that it is not a substitute: two instruments, two questions. One defect in this area does remain a working gate — the one that removes the doorbell fence, which is the SeqCst fence the suppression protocol needs and whose absence is deterministic enough to catch.

If you are evaluating this project and you care about the ring's correctness under weak memory, this chapter is the honest answer: the design is argued in docs/design/ring-scene-boot.html, the orderings are in the code with their reasoning at the access, the empirical test is known not to catch the defect it targets, and the proof that would settle it has not been built.

07

Proof, deliberately narrow

runs
State Built. Bounded model checking with Kani over three crates, on a nightly schedule rather than in verify, with deliberate defects that must each fail the harness stating the property they break.

Proof here is targeted rather than aspirational. The project does not claim a verified kernel and does not want one on the current schedule; what it claims is that a small number of properties — the ones where being wrong is silent and catastrophic — have been checked exhaustively inside a stated bound.

Three proof crates, all outside the workspace
kernel/proofs   # the five capability properties
ring/proofs     # the peer-facing validation paths
abi/proofs      # the admission arithmetic RFC 0050 put there

cargo xtask prove [harness]   # every harness, at both bounds, then every defect
cargo xtask lint-proofs       # they still compile against the code they prove

They are excluded from the workspace rather than absent from it, and the reason is a rule worth stating generally: a verification tool's toolchain is the tool's business. Kani installs its own rustc, which is not the one pinned in rust-toolchain.toml, and a workspace member would be built by cargo xtask test under the pin — which buys nothing and breaks on the day the two compilers disagree. RFC 0022, and RFCs 0053 and 0057 for the two ways a proof crate reaches the code it proves.

Proving the file that ships

A proof of a copy is a proof about the copy. The capability properties are proved over the file the kernel actually ships — compiled a second time through #[path] against stand-ins — rather than over a reimplementation written for the checker. RFC 0053 makes that a requirement and also requires each proof to state its bound, because an unbounded claim from a bounded checker is the most common way a verification result is oversold.

Where the bound falls is chosen rather than accepted. Handles are unbounded across the whole 32-bit space and rights across the whole rights lattice, because those are the inputs an attacker controls. The admission arithmetic is proved over every demand and every machine shape up to a small core count, and the two properties about the walk are proved again at a much larger one.

Two traps this avoids, both worth stealing

  • Table contents are bounded by construction, not by assumption. A harness never writes a table slot. It runs the real operations with symbolic operands, so the only states reachable in the proof are the states the table can actually reach — which means no proof holds for a state that cannot exist. A harness that populated the table directly would prove things about impossible tables and miss things about possible ones.
  • The ring is proved against bytes, not against a struct. The peer-facing paths take a region of symbolic bytes handed to the real adoption path, rather than a struct of fields the harness itself constructed. ring/src/mapping.rs names that as the trap: a harness that builds a well-formed struct has assumed away exactly the hostile input the validation exists for. RFC 0057.

And the proofs are themselves tested

Deliberate defects are injected into the proved code, and each must fail the harness stating the property it breaks — and no other. A proof that passes on a build with a known defect proves nothing, and the "and no other" half is what catches a harness that has become a blunt instrument asserting something broader than it claims.

The registry does not yet distinguish a proved result from a counted one in a machine-readable way. RFC 0069 decides that it should — an evidence key with three values, and a rule that a claim quantifying universally is proved or is misworded — and that RFC is deliberately draft until the lint lands, so that a reader cannot find a rule there that the tree does not enforce. Chapter 10 has the rest.

08

Fuzzing the one surface

runs
State Built, with two committed corpora that ship in the release package. Coverage instrumentation was added deliberately early, while the kernel was small enough for it to be cheap.

Fuzzing an operating system is usually intractable because there is no single surface to fuzz — a conventional kernel presents hundreds of system calls, each with its own argument grammar. F presents one ring, and that is what makes this layer affordable. It is a case where a decision made for performance pays out somewhere entirely unrelated.

A hostile peer

cargo xtask hostile generates a hostile peer from a seed and runs it for a very large number of operations, requiring no panic, no memory unsafety and no hang. Two design choices carry it:

  • A run is episodes derived by identity, so a finding deep into a run replays in a moment rather than requiring the whole run to be repeated. Without this, a fuzzer that finds something at the end of a long run hands you a reproduction that takes as long as the original — which in practice means nobody reproduces it. RFC 0046.
  • A hang is a count, never a wall-clock timeout. This is the determinism substrate asserting itself: a wall-clock timeout is a nondeterministic oracle, so a hang detected that way is a finding that may not reproduce, on a fuzzer whose entire value is that findings reproduce.

Structure-aware, and why

Random bytes are a bad fuzzer for a structured format, and here the arithmetic is exact. A submission entry's first check is a zero word, which random bytes fail with probability 1 − 2⁻³². A purely random generator would therefore spend essentially all of its budget being rejected at the first branch and would never reach the validation logic it was pointed at. cargo xtask entries is structure-aware with coverage feedback for that reason. RFC 0048 — an entry is generated by its structure and kept by its coverage.

Both corpora — ring/corpus.txt and sim/corpus.txt — are committed to the tree and included in the release package, so a stranger's first run starts from everything that has ever been found rather than from nothing. There is no separate corpus to fetch, which is a deliberate choice about what a reproduction should cost somebody who was not there.

Two instruments, two counts, both reported

Miri also covers the memory-unsafety property, at a much smaller operation count, under a much stronger notion of what counts as unsafe. Both numbers are reported rather than one being quoted — which matters, because quoting only the large count implies a strength the large count does not have, and quoting only Miri's implies a weakness the fuzzer does not have.

09

Provoking the real kernel

runs
State Built and in the CI gate. This is the layer the seven-layer taxonomy has no row for, and it is where most of this project's evidence currently comes from.

None of this is simulation, proof or fuzzing. It is the real kernel, in QEMU, being asked to do something that must not work. Every verb below boots the system more than once and requires the boots to disagree in a specified way.

CommandWhat it doesThe control that makes it mean something
faultBoots into each of six kernel faults.Each must be reported rather than survived. The exception path only runs when something has already gone wrong.
userSeven boots; a ring-3 process violates one isolation rule each.Six must fault and the kernel survive each; the seventh must not fault.
capNine boots; a process tries to hold authority it was not granted.Seven refused with the exact code each escape earns; one not refused at all — the process legitimately revokes, reads the unmapped page, and is stopped by the processor.
mutateA kernel built with a deliberate defect.Must go red with a panic in the log; the same boot without it must go green.
chaosKills every component under sustained load at seeded moments.The same load with nothing killed. No client may observe anything but added latency.
swapReplaces every component by the route its manifest declares.The same load with nothing replaced, and the crossed state compared against what the outgoing instance held.
cutCuts power at every write boundary in a publish, at block and byte granularity, honest and lying.Every cut must leave either the old root or the new one, with the tree it names resolving.
rollbackBreaks a generation and names the previous one to the loader.What comes back must be bit-identical: the root, every byte as delivered, and the generation rebuilt from source.
coresFour boots at differing core counts.A machine reporting eight and answering with two must still reach M0, holding the six and saying how far each got.
admissionA granted reservation under adversarial load.The same load unreserved, which must miss; and an over-subscription, which must be refused and run nothing.
attestFive boots asking what this machine is running.Is the answer the same twice; does modifying the frame move it; does the frame refuse a root it cannot measure its way to.

Read the third column, not the second. Almost every row is a pair, and the second half of the pair is what stops the first half passing for the wrong reason. A kernel that faults on everything passes six fault tests. A store that loses every write survives a power-cut test that only checks for corruption. A system that refuses every reservation never misses a deadline.

The cap suite's eighth boot is the one to understand if you only look at one. Seven boots are refused by the capability table with a named error code each. The eighth is not refused: the process revokes a capability it is fully entitled to revoke, then reads the page that revoke unmapped, and is stopped by the processor rather than by the table. That distinction — authority enforced by the table versus authority enforced by hardware after the table has already done the right thing — is the kind of thing a suite of refusals would never surface.

Why this has no row in the taxonomy

A taxonomy organised around simulation, proof and fuzzing has no natural category for running the real thing and trying to break it. The project's response was to leave the row absent and say so in docs/TESTING-STATUS.md rather than to file these verbs under whichever layer they least badly fit. Chapter 02 makes the general argument; this is the instance that prompted it.

The caveat that applies to this whole chapter is chapter 12's: the machine under all of it is an emulator.

The claims registry

mostly
State Built and gating. Several lints keep it agreeing with the documents. RFC 0069's evidence key is decided and deliberately not yet implemented, and that RFC is draft for exactly that reason.

A claim without a named baseline, a published workload and a one-command reproduction is an anecdote. claims/ is that requirement made mechanical, and it is the layer that decides which numbers this project is permitted to say out loud.

What an entry carries

A statement in prose; a baseline that is a configuration rather than a description of one; a workload with its parameters; the primary and secondary metrics; thresholds; the class of machine required; a one-command reproduction; the document and section that own it; and a diagnosis block, so that a red result arrives with its own first debugging step rather than with a question.

That last field is unusual and worth copying. A claim about ring submission latency records that a result far above target usually means false sharing on the cursors, and that a flat batch curve means the batch is not being amortised. The person who understood the number best was the person who registered it, and a registry that does not capture that hands the next reader a number and no thread to pull.

The five rules

  • The baseline is versioned with the claim. This is what stops a tuned-Linux comparison decaying into a stock-Linux comparison as the baseline configuration ages and nobody re-checks it.
  • Gating fails the build on regression; tracked records without gating. Muting a claim is a status change in a reviewable diff, never a comment in CI configuration.
  • Distributions, not summaries. A mean computed at collection time destroys what cannot be recovered, and systematically under-reports the stalls this architecture exists to eliminate.
  • Report instructions and joules per operation, not only nanoseconds. Those survive a hardware change and are far less noisy.
  • Regression detection is change-point, not threshold. Thresholds either miss real regressions or fire until everyone mutes them.

The split that is the honest part

A count may gate on this machine, and a time may not. The claims that currently gate are all counts — blast radius, hostile-peer operations, entry-validation coverage, admission refusals, deadline overtake, unmap churn — and a count is identical on any machine, because it is a fact about a deterministic run rather than about silicon. Every claim that is a time or a ratio of times is pending, and it is pending because the benchmark harness refuses to record a measurement in a container. That refusal is the harness working.

Where one piece of work produced both kinds, the claim was split rather than weakened. There are several such pairs in the registry: one entry gates on the count, and a sibling entry waits on the machine for the time. The alternative — one claim, gating, with the timing threshold quietly loosened until it passes in a container — is how a registry becomes decoration.

RFC 0069 makes that distinction a field rather than a convention: proved, counted or measured, with three rules behind it. A kind may not stand in for a stronger one, so a claim whose statement quantifies universally is proved or it is misworded. Only counted may gate on an ordinary machine. And a proved claim names its harness and nothing else — no baseline, because a proof is not faster or slower than Linux, and no hardware, because a solver's verdict does not depend on the machine it ran on.

The lints that keep it true

LintWhat it refuses
lint-claimsA document citing a value the claim no longer has. A number in a document is never a second copy of a claim.
lint-claim-ownersA claim that does not name the document owning it. A claim nobody owns is a claim nobody can be asked about.
lint-reproduceA published reproduction command that no longer resolves inside the tree.

cargo xtask claims --render rewrites a document's cited values from the registry, so the documents are generated from the numbers rather than being a parallel account of them. And cargo xtask reproduce is the entry point for somebody who was not there: it prints the claim, the commit, the class of machine required and what this machine is, runs the claim's own published reproduction, and ends by saying plainly whether the number was recorded.

The machine a number may be taken on

a file
State claims/runner-class-A.md is a complete specification. It is not a machine, and no machine matching it exists in this project. Every timing claim in the registry is waiting on that and says so.

A timing measurement is only recorded on a machine that can defend it. Anywhere else — a laptop, a shared cloud runner, the development container — the workload still runs, the distribution is still drawn and printed, and recording is refused with the reason. A number with no environment attached is how a benchmark becomes marketing, so the default is to refuse.

What the class requires

A granted hard-class reservation holds four things, and admission tests all four together or it is testing nothing. Class A is the class where all four are obtained by partition:

ComponentMechanismWhy a desktop cannot do it
A physical coreisolcpus, both SMT siblings taken as a unit.A schedulability test that counts threads has already conceded the tail it was run to bound.
Memory bandwidthresctrl MBA or SMBA.Consumer silicon does not offer it.
Last-level cacheresctrl CAT or L3 QoS.Dropped from client parts years ago. This is the single constraint that rules out a workstation.
Pre-faulted memory1 GiB hugepages, populated and locked.Faulted, not merely allocated — so no fault, tier migration or compaction lands inside a deadline.

Partitioning by exclusion — holding co-resident cores idle — is a legitimate reservation and is not this class. A machine without the cache and bandwidth controls needs a different class name with its own file, because reusing this one is how a class decays into whatever hardware was to hand.

The failure mode the whole apparatus exists for

The environment variable is an assertion, not a measurement. No code in this tree can tell a class-A machine from a workstation with F_ENVIRONMENT set by hand. What the tree can do is two things: fail closed on an unset or unrecognised value, so that everything else refuses by default; and require that the record of how each reservation component was obtained travels with every number. A number whose record says "by exclusion" for a component the class requires by partition was not taken here, and a reviewer can catch that by reading one page.

The file is honest about its own limit in the same terms: a file is not a machine. Nothing in this repository can buy hardware. What a specification can do is make the purchase decidable and make the cheat visible.

The baseline, and the asymmetry that raises it

The baseline is "tuned Linux, configured by someone trying to win", and it is a directory of applied configuration with a verifier beside it rather than a sentence — because a sentence cannot be re-run, and therefore cannot be found to have stopped being true.

Two judgements in it are worth reading if you suspect this apparatus of flattering F, because they are where flattery would live:

  • Speculative-execution mitigations are left on and recorded. The only thing that makes a comparison mean anything is that the setting is identical on both sides. Turning them off flatters both sides and describes a machine nobody deploys.
  • Transparent huge pages are off for F and on for the baseline. F maps its own 1 GiB pages and never uses Linux's, so never is right on F's side; a baseline handed small pages on that account would be a machine nobody configures, so always is right on the other. The asymmetry raises the baseline — and the file says in as many words that this is the direction a sceptical reader should check first.

Turbo off, uncore frequency fixed, C-states shallow, prefetchers left at defaults and recorded, no hypervisor, ECC, cooling with headroom so that the six-hundredth second of a run is the same machine as the first. The full list, the kernel command line and a seven-point verification checklist a stranger can work through are in claims/runner-class-A.md.

The honest gaps

true
State True at the time of writing and the fastest-moving chapter in the book. docs/TESTING-STATUS.md is the maintained version; where this disagrees with it, that file is right.

This chapter is not a disclaimer. It is the part of the apparatus with the most information in it, and a reader deciding whether to take this project seriously should weigh it more heavily than any green check in the preceding nine chapters.

The largest one, and the easiest to miss

The kernel has never run on bare metal. It has run outside QEMU three times, all on virtual machines. Three further attempts on a Threadripper host did not reach M0 ok at all — the first died inside core bring-up, and two RFCs came out of that; the last ran to ring 3 and refused its own stack selector at the first interrupt, because the emulator had been forcing privilege bits this kernel forgot, which is a third RFC. Everything else this book reports is an assertion about an emulator: the APIC enumeration, the memory map, the UART, application-processor startup, and every datapath result. Nothing here is failing. The tests pass, the boots are green, and the subject of nearly every one of them is QEMU.

Two consequences worth knowing before that first metal boot rather than after. The trace hash will differ on hardware, because the memory map and core count are in the log by design and QEMU's are pinned. And the kernel supports a fixed maximum number of logical processors, so a larger machine leaves the rest asleep and says so on its own line.

The rest, in the order they would bite

  • The IOMMU stage has never met real firmware, and under UEFI it cannot. The boot found no checksummed root pointer in either legacy window, because the boot protocol has no field for it and UEFI does not leave one where this kernel can scan. That is structural and will happen on every UEFI machine, including the one the project is waiting for. The kernel fails closed and says so, which is the refusal policy working rather than a defect — which is precisely why it needs a line here, since nothing goes red.
  • Generation selection has never run on hardware. All three boots outside QEMU printed that no generation was selected, so the frame measured itself and had nothing to compare against. Under QEMU both tokens are on every command line, so that half of the attestation design is exercised constantly on an emulator and nowhere else. Found by the third boot and fixed in the same change — but the fix is tested under QEMU and staged, not booted.
  • The user-interrupt doorbell is written and has never executed. The construction refuses on a machine that does not report the hardware, which is every machine this project can reach; QEMU's emulation implements no part of it. What is tested is the refusal and the selection logic. Do not read the suppression test passing on three paths as three paths having run: two have.
  • The doorbell count in the boot log is a boot count, not a measurement. It is taken over the two operations the self-test performs, which is enough to show the count exists and is not always one. It is not doorbells per operation under load, and it is deliberately not registered as a claim.
  • The litmus suite does not catch the defect it was written for. Chapter 06, and the sharpest item on this list.
  • The state tree publishes nothing that varies with time. Counts, cores, ring tallies, capability slots, datapath tallies — not the timer's counters, not a stamp, not a hash of anything live, because the boot log is the reproduction artefact and a tick count in it would make two runs of one commit disagree for a reason having nothing to do with the kernel. That exclusion is a decision with a reversal condition, not a gap: it lifts when the boot log stops being the reproduction artefact.

Gaps that are quantities rather than sentences

Several gaps in this tree are declared constants that a lint compares against the tree, so each goes red both when it grows and when the reason for it stops being true. A gap written as prose can only be found to have grown by somebody reading the prose; a gap written as a number that something checks cannot quietly persist after it has been closed. One of them was paid recently, and the constant, its row and the wall it described all went together — which is the mechanism working rather than the list shrinking.

cargo xtask lint-owed is the sharpest of these: it lists reversal conditions that have fallen due and are unpaid, and it fails on the day one is paid and nobody updates the documents that describe the old shape. That is the difference between a debt and a wish.

How to read the rest of this book now

The instruments in part II are real and most of them are good. The thing to hold onto is what each one is evidence about: the simulator is evidence about components and declares that it is not evidence about the frame; the proofs are evidence inside a stated bound and name the bound; the fuzzer is evidence about one surface; the boot suite is evidence about an emulator; and the registry's timing claims are evidence about nothing yet, because the machine they require does not exist.

Stated that way it sounds like a thin case, and at M0 it is a thin case — that is what M0 means. The argument this book actually makes is narrower and, I think, harder to dismiss: the apparatus is capable of telling this project it is wrong, and has already done so at least once in a way that cost a green check.
