Execution plan · seven epochs

The Long Plan

Everything the five design documents and the decision record imply, ordered into seven epochs, each closed by a gate that is a test rather than a feeling, and each followed by a release a stranger can reproduce. The testing environment is not a section at the end: it is one of the four movements in every epoch, because the output of this project is measurements and an unmeasured system has produced nothing.

01

How the plan is meant to be used

The plan lives in two places on purpose. This document holds the reasoning, the gates, the testing environment and the release contract — the parts that are argued rather than ticked. TODO.md holds the list, and is meant to be edited constantly by anyone.

Four movements, every epoch Decide, build, prove, release. They interleave in practice and are separated in the list because the failure mode of a project like this one is doing all of the building and none of the proving, then discovering at the end that nothing measured is defensible. Naming the movement a task belongs to makes an unbalanced epoch visible while there is still time to rebalance it.

Three rules make the list workable by someone who did not write it:

  • Every task carries an exit. The observation that closes it — a test that passes, a number recorded, a document merged. A task with no exit is a wish, and wishes are what make a plan unfalsifiable.
  • Every task carries its blockers. The list is a dependency graph rather than a sequence, so an unblocked task can be picked up by anyone without asking. That is the whole of what freely realizable means at the task level.
  • IDs are permanent and nothing is deleted. A dropped task is marked dropped with its reason and stays in place. The reason is more valuable than the task was.

Effort figures throughout are the architecture document's, unchanged: they assume a competent team that is not also inventing new research, and they are the honest reason to narrow scope before writing code rather than after.

03

The gates

A gate is what closes an epoch, and each one is written as an observation somebody could make and be wrong about. The milestone ladder already works this way — a done-criterion that is a test rather than a feeling — and this extends the same discipline to the larger units.

G0ground truth
A capability-restricted process talks to the kernel entirely through a ring, touches nothing it was not handed, and the suite runs under one command with jitter and ring throughput gating every commit. Plus the two things phase 00 does not currently promise and should: a seed and a commit reproduce a run byte for byte on somebody else's machine, and a stranger reproduces both published numbers from the README.
G1the datapath
A driver is killed under sustained load and no client observes anything but latency. And the apparatus half, which matters more: a bug injected anywhere is found by an overnight seed sweep and arrives as a reproduction command rather than as a symptom somebody has to chase.
G2state
Break the system deliberately and roll it back. Replace a running component without dropping work. Cut power at every write boundary of a publish and never observe a state that was not one of the two intended ones.
G3the interface
Input to photon under 14 ms at p99, measured by photodiode under load, with no software timestamp in the measurement path — and one application driving four projections with no projection-specific code in it.
G4the platform
Someone outside the team ships something, against a negotiated ABI, without reading the kernel source. This is the only gate whose outcome is not under the team's control, which is exactly why it is a gate.
G5real hardware
An unmodified vendor driver runs confined, restartable and without ambient authority on real silicon, and the cost of that confinement is a published number. Nobody has published that number, which is why this gate is also a result.
G6the AI substrate
Concurrent inference and audio, both inside their deadlines, on one machine, with weights shared from the store — against a baseline configured by someone trying to win.
G7the result
A competent skeptic tries to refute a published claim using only what is in the release package, and fails. Every gate before this one exists to make this one possible to attempt.
04

The proving ground, built in order

Proving Ground specifies seven layers and docs/TESTING-STATUS.md records that three of them exist in some form. This is when each layer arrives, and why it arrives then rather than earlier or later. The rule behind the ordering is the one that put the determinism substrate at M0: build the apparatus at the point where it is cheapest, which is almost always before it is needed.

LayerArrivesWhy thenReaches full strength
L0 — determinism substratebuilt M0, done The one property that cannot be retrofitted. Everything else on this page depends on it. E0, when the reproduction check runs across two machines rather than one.
L1 — deterministic simulationhook only E1 It needs components to substitute and devices to model, and neither exists before the datapath. The hook is already in place, which is the expensive half. E2, when a power-cut model turns crash consistency into a swept property rather than a hope.
L2 — concurrency and memory modelstress only E0 stress, E1 checking Litmus tests are cheap now and catch the obvious. Model checking explores what the memory model permits, which is a different question and worth its cost once the protocol stops moving. E1–E2, with the AArch64 job kept non-advisory throughout.
L3 — proofabsent E1 (capabilities), E2 (frame) Proof against a moving target is wasted work. The capability properties stop moving at M4; the frame stops moving around phase 02. E2. Deliberately narrow: the frame's invariants and the protocol state machines, never the system.
L4 — fuzzinginstrumentation only E1 Coverage instrumentation is added at E0 because instrumenting a mature kernel is painful and instrumenting a two-thousand-line one is free. The fuzzers themselves need a real entry surface. E1, with the corpus committed and published as a release artifact.
L5 — performance regressionharness only E0 harness, E2 detection Change-point detection needs history to reason about, so the history is stored from the first measurement and the detector is written when there is a year of it. E2. Thresholds are never introduced as a stopgap; they train everyone to ignore the signal.
L6 — hardware in the loopabsent E3 rig, E5 lab Correctly deferred: there is nothing to point a photodiode at until a compositor exists. The lab arrives with real hardware. E5, when bisect runs unattended on the machine the claims are collected on.
L7 — claims registrybuilt, one entry M0, done Registering the apparatus before the numbers is what makes it grow with the system instead of being retrofitted onto it. Every epoch. A claim is added with the capability it measures, not after it.
L8 — the state treeproposed E0 v0, E1 everywhere Not in the original seven. It belongs here because it is what every other layer reads: the simulator's oracle, the claims registry's source, and the answer to what a component is doing right now. E2, when comparing two whole-system states is comparing two hashes.
05

The testing environment, concretely

Eight components. The thing worth noticing is how much of it falls out of architectural decisions made for other reasons — one ring interface gives one interception point, no ambient authority gives no hidden channels, user-space drivers make a modelled device a component substitution, content-addressed state makes whole-system comparison a hash comparison. The environment is cheap here in a way it is not anywhere else, and that is a claim in its own right.

01 — the simulator
Virtual time · seeded ordering · device models · component substitution · snapshot and restore
Catches: ordering bugs, protocol violations, fault-handling paths that are never taken in production. Gives: a failure that reproduces from a seed and a commit, and a bisect that re-enters at simulated minute 39 instead of re-running the first 39.
02 — fault injection
Allocation failure · translation faults · device page-fault latency · peer death mid-operation · torn doorbell · partial write · power cut
Catches: the paths that only run when something has already gone wrong, which is where the bugs that matter live. The hook exists; each class is one file once code asks its Env whether an operation should fail.
03 — the fuzzers
Coverage-guided entry fuzzing · a hostile peer that lies about its cursors and its epoch · a committed corpus
Catches: everything a compromised or crashed peer can do to the one surface that accepts untrusted input. The kernel must never panic, corrupt or hang — a billion hostile operations is the bar.
04 — proof and model checking
Litmus tests · memory-model checking · bounded proof on capability properties · deductive proof on frame invariants
Catches: what sampling cannot — the interleaving one machine never happened to produce. Deliberately narrow: the frame and the protocols, never the system, at a fraction of the seL4 cost and with none of its guarantee.
05 — bench and claims
Full distributions · instructions and joules per operation · versioned baselines · change-point detection · gating status in a reviewable diff
Catches: the regression that ships because it was 4% and nobody was watching. Enforces: that a number without a named baseline and a reproduction command never reaches a document.
06 — hardware in the loop
Photodiode capture · external input injection · external energy meter · netboot, serial, power cycling · unattended bisect
Catches: the difference between a number the system reports about itself and a number an instrument reports about the system. The latency claim is not credible measured any other way.
07 — the state tree
Hierarchical typed state, published continuously · hashed at snapshot boundaries · readable with no debug build and no debugger
Catches: divergence, at the moment it appears and in the subtree where it happened, instead of as a symptom at the end of a run. Also what makes a claim and a live reading the same number.
08 — continuous integration
Pull-request gate · nightly sweeps · weekly checking and soaks · per-release reproduction
Catches: the slow decay of everything above. A muted job is a deleted job with extra steps, so the schedule is designed to stay green rather than to stay loud.

07

Continuous integration, and its time budgets

Four cadences. The budgets are as load-bearing as the contents: a pull-request gate that takes forty minutes gets bypassed, and a bypassed gate is worse than no gate because it produces the belief that something was checked.

CadenceBudgetRunsOn failure
Pull requestevery change < 10 min The four policy lints; workspace tests; the kernel in emulation asserting its exit code; litmus on two architectures; every gating claim; the two-machine reproduction check. Blocks the merge. No exceptions and no override path — an override path becomes the path.
Nightlyevery day < 8 h Seed sweeps across every scenario with automatic minimisation; coverage-guided fuzzing from the committed corpus; the hostile peer; fault-class sweeps; the crash-consistency model from E2. Files a reproduction command, not a symptom. A sweep failure that cannot be minimised is itself a bug in the apparatus.
Weeklyevery week < 48 h Memory-model checking; the proofs; reproducible-build verification across two machines; the compatibility matrix; long soaks once hardware exists. Loud. These are the jobs that get muted first, so muting one is a reviewable diff like everything else.
Releaseevery tag as long as it takes Everything above, plus the full claim set re-measured, the package built twice on two machines and compared by hash, and the reproduction guide executed from a clean machine by someone who did not write it. No release. A release whose numbers were not re-measured is a claim about the past.

Noise control is part of the design, not a tuning exercise. Measurement runs on pinned cores with a stated frequency policy, reports instructions and joules per operation alongside nanoseconds because those survive a hardware change, stores distributions rather than summaries, and never compares across runner classes. Change-point detection over stored history replaces thresholds, because a threshold either misses the real regression or fires until everybody stops looking.

08

What a release is

For a product, a release is software somebody installs. For a research vehicle whose deliverable is defensible measured claims, a release is an evidence package, and the software is one of its contents. That reframing decides everything else in this section.

The release contract Every published number in a release can be re-derived by a stranger, from the package, with one command, on hardware they can buy. If that is not true of a number, the number is not in the release. This is the claims-registry rule applied to the whole artefact rather than to a single entry.
The package containsBecause
The source, at a tagObvious, and insufficient on its own — which is the point of everything below it.
The claims snapshotEvery number the release asserts, with its baseline, its workload, its distribution and its reproduction command. Machine-readable, so documents render from it rather than restating it.
The baseline configurationThe tuned Linux the comparison was made against, as configuration rather than as prose. This is what stops a tuned comparison decaying into a stock one as the baseline ages and nobody re-checks.
The seed corpus and scenario setSo a third party can run the same sweeps, and so a reported bug arrives as a seed rather than a description.
A content-addressed system imageOne hash naming an entire bootable generation. Reproducing it from source and getting the same hash is a test, and it runs in the release job.
The dependency manifest and provenanceWhat went in, at what version, under what licence — with the imported subtree's terms kept distinct, because the licence boundary and the isolation boundary are deliberately the same boundary.
The honest-status pageWhat does not work, what was measured on emulated hardware, what is a hook rather than a system. TESTING-STATUS.md is this page and it ships with every release.
The decision recordEvery RFC, including the superseded ones, so that a reader can see what was reversed and why rather than only what survived.

Cadence is milestone-driven, never calendar-driven. A release happens when a gate closes. Dates on a research vehicle produce either padded gates or quiet ones, and both are ways of lying to yourself about where the project is.

Versioning is two numbers that mean different things. The release version tracks gates. The ABI version tracks the wire, with a floor and feature bits, and moves entirely independently — a component built against release 0.3 must keep working at 0.4 or the component model is decorative.

09

Freely realizable, stated as four things that must never be true

Transparency is easy to assert and hard to check, so it is stated here as negatives, each of which is falsifiable by anyone who tries.

  • No number exists that only we can reproduce. Every claim carries a command, the command runs from a clean checkout, and the release job proves it by having someone who did not write it run it on a clean machine.
  • No step exists that is not in the tree. If a build, a measurement or a release needs a script, the script is xtask and it is committed. Institutional knowledge in somebody's shell history is the standard way a project becomes unreproducible without anyone deciding it should be.
  • No dependency exists that cannot be replaced. Every immature bet carries a written fallback that is merely good rather than exceptional, and the fallback is re-checked once per epoch. A dependency whose failure would cost a bet rather than a claim is not taken at all.
  • No result is published without its cost. Reservations leave capacity idle. Content addressing is bad at small random writes. The frame still needs a reboot. Each of those goes beside the result it qualifies, not in a rebuttal after somebody finds it.

The positive form of all four is the contribution path: someone who has never spoken to the team can clone the tree, run one command, get a green build, pick any unblocked task from TODO.md, see its exit test, and know when they are done. That is the whole of what this plan means by realizable, and it is checkable at any moment by trying it.

10

Where this plan most likely fails

The failure modes of long plans are as well documented as the failure modes of new operating systems, and mostly consist of the plan being right about the work and wrong about the order.

E3 eats everything
Four to ten person-years is the widest range in the table for a reason, and the low end assumes a toolkit scope that has been narrowed hard. The mitigation is to reach G3 with the smallest interface that can carry the claim — one application, four projections — rather than a desktop.
The apparatus gets deferred
Every prove task competes with a build task that feels more like progress, and the prove tasks lose that comparison every single time it is made. The four movements exist to make the imbalance visible; the gates exist so it cannot be resolved by shipping anyway.
The ABI ossifies before it is right
Three corrections are cheap in E0 and expensive after E1, and by E4 the compatibility matrix makes them a negotiation about how to negotiate. This is the one place in the plan where the ordering is not a preference.
The baseline decays
A tuned Linux comparison becomes a stock Linux comparison by doing nothing at all for eighteen months. It is in the always-on list, it will still be the first thing skipped, and it is the single most effective way for this project's numbers to become worthless.
Scope arrives one reasonable item at a time
Mutable-path compatibility, a shell, a package ecosystem, wireless. Each is defensible alone; together they are the product obligations RFC 0002 exists to refuse. Anything dropped moves to a dropped marker with a reason, in a reviewable diff, so that re-adding it is also a decision.
11

Keeping the plan true

A plan is a document that decays faster than code, because nothing fails when it is wrong. Four maintenance rules, all cheap and all easy to skip:

  • The list is edited, not rewritten. Task IDs are permanent, dropped tasks keep their reasons, and the shape of what was abandoned stays visible.
  • Every gate closure updates the honest-status page. The distance between this plan and the tree is the number that matters most and the one nobody volunteers.
  • Every reversal is an RFC. The decision record is append-only and the reversals are the part worth keeping; the reasoning already lives in the design documents.
  • Re-read the risk register once an epoch. Fallbacks for immature dependencies, the unsafe percentage against its 10% reversal trigger, the baselines, and the two claims that would falsify a bet if they came back wrong.
The one-line version Seven epochs, seven gates, seven releases, and one contract: every number a stranger can re-derive. The testing environment is not the last epoch's work — it is the second movement of every epoch, and the reason the gates can be written as observations rather than as opinions.
